## 一、乒乓球球体检测

### 1.1 技术难点分析

乒乓球球体检测是整个分析流水线的基础环节，也是技术难度最高的环节之一。核心难点包括：

| 难点维度 | 具体参数 | 影响 |
|---------|---------|------|
| 球体尺寸小 | 直径仅 40mm，在 1080p 画面中仅占 10-30 像素 | 传统检测器对小目标召回率低；YOLO 默认输入分辨率下球体特征不足以区分 |
| 球速极快 | 专业比赛球速可达 15-35m/s（据 arXiv:2606.25620 文献记录） | 30fps 视频中帧间位移可达 0.5-1.2m，即球体可能在一帧内横跨大半个球台 |
| 运动模糊严重 | 高速运动 + 普通快门速度 → 拖影 | 球体在画面中呈现为模糊条纹而非圆形，显著增加检测难度 |
| 背景干扰多 | 运动员白色/橙色球衣、灯光反光、球台边线等 | 误检率上升，需颜色/形状/运动多特征融合 |
| 遮挡频繁 | 运动员身体、球拍遮挡 | 需要时序信息辅助，不能仅依赖单帧检测 |

> **来源**：arXiv:2004.09927 (TTNet, CVPR 2020)、arXiv:2509.18387 (BlurBall, 2025)、arXiv:2606.25620 (1000 Rallies)

### 1.2 现有研究与开源项目

#### 1.2.1 TTNet（OSAI 团队，CVPR 2020）

- **论文**：*TTNet: Real-time temporal and spatial video analysis of table tennis* (arXiv:2004.09927)
- **开源实现**：[maudzung/TTNet-Real-time-Analysis-System-for-Table-Tennis-Pytorch](https://github.com/maudzung/TTNet-Real-time-Analysis-System-for-Table-Tennis-Pytorch)
- **核心架构**：多任务神经网络，统一完成球检测（Global Stage + Local Stage 精细化）、事件检测（弹跳/擦网）、语义分割（人/球台/记分牌）
- **关键设计**：
  - 采用 heatmap 热力图方式检测球位置，而非传统 bounding box，更适合小目标
  - 输入为连续 9 帧图像拼接（`9×320×128`），利用时序信息对抗运动模糊
  - 事件检测（弹跳/擦网）的 PCE（Percentage of Correct Events）达 ~97%
- **适用性评估**：⭐⭐⭐⭐⭐ — 专门针对乒乓球设计，是当前最贴合的方案

#### 1.2.2 TrackNet 系列（V1 → V5）

TrackNet 是体育球体追踪领域最成熟的算法系列，从 V1 到 V5 持续演进：

| 版本 | 论文/来源 | 核心改进 | 精度与速度 |
|------|----------|---------|-----------|
| TrackNetV1 | 2019, ACM MMAsia | 首创 heatmap 编码器-解码器范式 | Recall 有限 |
| TrackNetV2 | 2020, ACM MMAsia | MIMO（多输入多输出）架构，大幅提升吞吐和精度 | 基准版 |
| TrackNetV3 | 2023, ACM MMAsia ([GitHub](https://github.com/alenzenx/TrackNetV3)) | Inception-style 块堆叠，引入 Attention 机制 | 精度最高但延迟约为 V2 的 3 倍 |
| TrackNetV4 | 2024 (arXiv:2409.14543) | 融合可学习运动注意力图（Motion Attention Maps），即插即用 | 在 V2/V3 基础上进一步提升，遮挡场景改善明显 |
| TrackNetV5 | 2025 (arXiv:2512.02789) | 残差驱动时空细化 + 运动方向解耦 | 最新成果，精度/速度平衡更优 |

- **开源代码**：TrackNetV3 GitHub 实现已公开（285+ stars）
- **TrackNetV2 Dataset**：包含 10 场网球比赛标注数据，约 2.59GB，含球和击球标注
- **适用性评估**：⭐⭐⭐⭐ — 原始设计针对网球/羽毛球，但架构可直接迁移到乒乓球

> **来源**：arXiv:2409.14543 (TrackNetV4)、arXiv:2512.02789 (TrackNetV5)、GitHub: alenzenx/TrackNetV3

#### 1.2.3 BlurBall（2025，最新成果）

- **论文**：*BlurBall: Joint Ball and Motion Blur Estimation for Table Tennis Ball Tracking* (arXiv:2509.18387)
- **核心贡献**：联合估计球位置和运动模糊核，直接处理运动模糊导致的球体拖影问题
- **适用性评估**：⭐⭐⭐⭐ — 直接针对乒乓球场景，解决运动模糊这一核心痛点

#### 1.2.4 基于图神经网络的高速球追踪（Nature, 2024）

- **论文**：*Fast moving table tennis ball tracking algorithm based on graph neural network* (Nature Scientific Reports, 2024)
- **数据集**：20 段独立视频，13,950 帧，6,027 个标注乒乓球
- **视角覆盖**：侧视（Side-Facing）、正视（Directly-Facing）、球员正视（Player-Facing）
- **适用性评估**：⭐⭐⭐ — 创新性强，但工程落地复杂度较高

#### 1.2.5 YOLO 系列用于乒乓球检测

多个实践已验证 YOLO 在乒乓球检测中的可行性：

- **YOLOv3**：Zhang 等（2019）首次将 YOLOv3 应用于乒乓球检测，实现了较好的实时性能
- **Tiny-YOLO**：Wang 等（2020）在嵌入式设备上实现了 60FPS 的检测速度
- **YOLOv8/v11**：有研究者使用 YOLOv8/v11 微调乒乓球检测，并在 TTStroke-21 数据集上验证
- **YOLO11n**：Daniel Duarte 的项目使用了微调的 YOLO11n 模型进行球检测，并配合自定义 TrackNet-style 热力图 CNN 作为更强替代方案

> **来源**：CSDN 毕业设计专栏（YOLO 乒乓球检测）、danielduartecv.com、arXiv:2511.04126

#### 1.2.6 TOTNet（2026，最新）

- **论文**：*TOTNet: Occlusion-aware temporal tracking for robust ball detection in sports videos* (CVIU 2026)
- **开源**：[AugustRushG/TOTNet](https://github.com/AugustRushG/TOTNet)
- **核心**：专门解决遮挡场景下的球体检测，利用时空信息
- **适用性评估**：⭐⭐⭐⭐ — 遮挡是乒乓球场景的常态，此方案针对性强

#### 1.2.7 RacketVision（AAAI 2026 Oral）

- **论文**：*RacketVision: A Multiple Racket Sports Benchmark for Unified Ball and Racket Analysis*
- **开源**：[OrcustD/RacketVision](https://github.com/OrcustD/RacketVision)
- **覆盖范围**：羽毛球、乒乓球、网球三项球拍运动
- **核心贡献**：首个大规模细粒度标注数据集，包含球拍姿态估计、球位置标注和轨迹预测
- **代码和数据已于 2026 年 4 月发布**
- **适用性评估**：⭐⭐⭐⭐⭐ — 直接覆盖乒乓球，提供球追踪、球拍姿态估计、轨迹预测三大任务的基准

### 1.4 推荐技术路线

**方案 A（推荐）：TTNet 热力图检测 + YOLO 辅助验证**

```
输入视频帧 (连续 9 帧)
    ↓
TTNet Global Stage (球位置热力图预测)
    ↓
TTNet Local Stage (位置精细化)
    ↓
[可选] YOLO11n 微调模型 (bounding box 验证)
    ↓
球位置坐标 + 置信度
```

**方案 B（备选）：TrackNetV2/V4 迁移 + 自标注数据微调**

```
输入连续帧序列
    ↓
TrackNetV2/V4 (预训练权重 → 乒乓球数据迁移学习)
    ↓
球位置热力图 → 坐标提取
    ↓
[后处理] 运动一致性过滤（去除明显误检）
```

**方案 C（快速验证）：YOLO11n + 光流法**

```
单帧输入 → YOLO11n (微调) → 球 bounding box
    ↓
光流法辅助（帧间运动一致性）
    ↓
球位置坐标
```

> **方案选型建议**：原型验证阶段建议方案 A 优先（TTNet 已有完整 PyTorch 实现，直接适配乒乓球场景），方案 C 作为快速 baseline 对照。

## 二、球体追踪

### 2.1 技术背景

乒乓球追踪的核心挑战在于：球体小（容易丢失）、速度快（帧间位移大）、频繁遮挡（运动员/球拍遮挡）。单纯的检测器逐帧检测会导致：
- 遮挡帧丢失球位置 → 轨迹断裂
- 误检帧引入虚假轨迹点 → 轨迹噪声
- 无法区分多个球（训练多球场景） → ID 切换

### 2.2 现有追踪算法评估

#### 2.2.1 DeepSORT

- **原理**：在 SORT（Simple Online Realtime Tracking）基础上加入深度外观描述符（Deep Association Metric），通过卡尔曼滤波预测 + 外观特征匹配
- **开源**：[nwojke/deep_sort](https://github.com/nwojke/deep_sort)
- **适用性评估**：⭐⭐ — DeepSORT 设计针对行人追踪，乒乓球场景下外观特征区分度不足（球都长得一样），核心优势无法发挥

#### 2.2.2 ByteTrack

- **原理**：利用低置信度检测结果（而非丢弃），通过二次关联找回被遮挡的目标
- **适用性评估**：⭐⭐⭐ — 对遮挡场景有改善，但乒乓球"低置信度检测"通常意味着真正的误检（背景干扰），而非被遮挡的球

#### 2.2.3 TrackNet 内置追踪

- TrackNet 系列本身通过连续帧输入（如 9 帧拼接）隐式实现了时序追踪，输出的是连续轨迹而非单帧检测结果
- **适用性评估**：⭐⭐⭐⭐⭐ — 与检测器一体化，无需额外的多目标追踪算法

#### 2.2.4 卡尔曼滤波 + 运动模型

- 传统乒乓球机器人领域常用方案：颜色分割 + 卡尔曼滤波 + 运动学模型（抛物线/反弹模型）
- 优势：计算量极小，可在嵌入式设备实时运行
- 劣势：依赖固定颜色假设、固定机位、良好光照，泛化能力弱
- **适用性评估**：⭐⭐⭐ — 作为后处理滤波器补充使用，不适合作为主追踪方案

### 2.3 推荐技术路线

**推荐方案：检测 + 物理约束追踪（双轨融合）**

```
帧 t 的球检测结果 (x_t, y_t, confidence_t)
    ↓
    ├── Track 1: 卡尔曼滤波预测 (匀速运动模型)
    │     ↓ 预测位置 (x_pred, y_pred)
    │
    ├── Track 2: 物理运动模型 (抛物线 + 反弹约束)
    │     ↓ 预测位置 (x_phys, y_phys)
    │
    └── 融合：加权平均 / 数据关联
          ↓
    最终轨迹点 (x_t, y_t)
          ↓
    [遮挡帧] 使用预测值补全
    ↓
连续轨迹 → 事件检测（弹跳/擦网/击球）
```

**关键参数**：
- 卡尔曼滤波状态向量：`[x, y, vx, vy]`（位置 + 速度）
- 过程噪声协方差：根据球速范围（15-35m/s）调参
- 遮挡容忍帧数：建议 3-5 帧（30fps 下约 100-170ms）

### 2.4 弹跳/擦网事件检测

基于连续轨迹的曲率变化检测事件：

- **弹跳检测**：Y 方向速度方向突变（从向下变为向上），且 Y 坐标位于球台高度范围
- **擦网检测**：轨迹在球网位置附近发生显著偏折
- **击球检测**：速度方向突变 + 加速度峰值，且位置靠近某一方运动员

> **参考**：TTNet 的事件检测模块（Events Spotting）实现了 ~97% PCE，可直接复用

## 三、球台检测与坐标映射

### 3.1 技术目标

从视频画面中检测球台位置，建立像素坐标 ↔ 球台真实坐标的映射关系，从而：
- 将球的像素轨迹转换为真实物理轨迹
- 估算落点在球台上的具体位置
- 计算球速（基于真实物理距离）

### 3.2 球台检测方法

#### 3.2.1 YOLO 目标检测（球台 bounding box）

- 使用 YOLOv8/v11 检测球台整体位置，输出 bounding box
- 优势：检测稳定，训练数据标注成本低
- 劣势：bounding box 不提供角点精确位置，无法直接用于单应性矩阵计算
- **适用阶段**：初步定位球台区域，缩小后续处理范围

#### 3.2.2 关键点检测（球台四角 + 中线端点）

- 使用 HRNet / ResNet50 关键点检测架构（参考网球场地检测方案 arXiv:2511.04126）
- 标注球台 4 个角点 + 2 个中线端点 + 4 个边线关键点，共 10 个关键点
- **参考实现**：Daniel Duarte 的项目使用 YOLO pose model 检测球场关键点，计算单应性矩阵
- **OpenTTGames 数据集**已包含球台语义分割掩码，可用于训练

#### 3.2.3 语义分割（球台区域）

- TTNet 的语义分割模块可直接检测球台区域
- 输出：人/球台/记分牌的像素级分割
- **适用阶段**：作为关键点检测的补充验证

### 3.3 单应性矩阵与坐标映射

#### 3.3.1 原理

单应性矩阵（Homography Matrix）描述两个平面之间的投影变换关系。乒乓球台是一个平面，从相机视角到俯视图存在一个 3×3 的单应性矩阵 H。

```
[pixel_x]       [real_x]
[pixel_y] = H × [real_y]
  [1  ]          [  1   ]
```

#### 3.3.2 实现（OpenCV）

```python
import cv2
import numpy as np

# 球台真实尺寸（标准 ITTF 规定）
# 长 2.74m × 宽 1.525m
# 球台四角在世界坐标系中的坐标（单位：米）
real_corners = np.array([
    [0.0, 0.0],      # 左上角
    [2.74, 0.0],      # 右上角
    [2.74, 1.525],    # 右下角
    [0.0, 1.525],     # 左下角
], dtype=np.float32)

# 画面中检测到的球台四角像素坐标（由关键点检测器输出）
pixel_corners = np.array([
    [px1, py1],  # 对应左上
    [px2, py2],  # 对应右上
    [px3, py3],  # 对应右下
    [px4, py4],  # 对应左下
], dtype=np.float32)

# 计算单应性矩阵
H, mask = cv2.findHomography(pixel_corners, real_corners, cv2.RANSAC, 5.0)

# 将球像素坐标转换为真实坐标
ball_pixel = np.array([[bx, by]], dtype=np.float32).reshape(-1, 1, 2)
ball_real = cv2.perspectiveTransform(ball_pixel, H)
# ball_real[0][0] = [real_x, real_y] 单位：米
```

#### 3.3.3 球台关键点

乒乓球台标准结构（ITTF 规定）：

| 关键点 | 描述 | 真实坐标 (m) |
|--------|------|-------------|
| P1 | 球台左端线左角 | (0, 0) |
| P2 | 球台左端线右角 | (0, 1.525) |
| P3 | 球网左侧 | (1.37, 0) |
| P4 | 球网右侧 | (1.37, 1.525) |
| P5 | 球台右端线左角 | (2.74, 0) |
| P6 | 球台右端线右角 | (2.74, 1.525) |

> 至少需要 4 个不共线的对应点即可求解 H 矩阵，建议标注全部 6 个点提升鲁棒性。

### 3.4 落点估算技术路线

```
连续球轨迹 (像素坐标序列)
    ↓
单应性矩阵 H (像素 → 真实坐标映射)
    ↓
真实坐标轨迹 → 检测弹跳事件
    ↓
弹跳点真实坐标 → 落点区域判定
    ↓
落点区域：球台分为 6-9 个区域
    ↓
落点热力图 + 落点分布统计
```

**落点区域划分**（参考教练分析惯例）：


## 四、人体姿态估计与动作识别

### 4.1 技术目标

从视频中检测运动员姿态，识别击球动作类型（正手攻/反手攻/正手拉/反手拉/发球/搓球等），为技术统计提供数据。

### 4.2 姿态估计方案

#### 4.2.1 MediaPipe Pose（推荐 — 原型验证首选）

- **模型**：BlazePose，检测人体 33 个关键点
- **优势**：
  - 纯 CPU 实时运行（~30 FPS），无需 GPU
  - Google 官方维护，Python/JavaScript/移动端全平台支持
  - 已有体育场景实践（sport-vision 项目验证了 MediaPipe 在羽毛球/网球中的可行性）
- **关键点**：重点关注手腕(15,16)、手肘(13,14)、肩膀(11,12)、髋部(23,24)、膝盖(25,26)、脚踝(27,28)
- **开源参考**：[MindDock/sport-vision](https://github.com/MindDock/sport-vision) — 基于 MediaPipe 的球拍运动分析系统，实现了发球、扣杀、正手、反手等 6 种动作识别
- **适用性评估**：⭐⭐⭐⭐⭐ — 原型验证最佳选择

#### 4.2.2 MMPose / RTMPose

- OpenMMLab 体系下的姿态估计工具箱，提供 2D/3D 姿态估计
- 精度更高但部署复杂度也更高
- **适用性评估**：⭐⭐⭐⭐ — 适合后续产品化阶段精度提升

#### 4.2.3 DensePose

- Facebook/Meta 开发，将人体映射到 3D 表面模型
- 有乒乓球场景研究使用 DensePose 提取人体形态后输入 C3D 网络
- **适用性评估**：⭐⭐⭐ — 过于重量级，原型验证不推荐

### 4.3 动作识别方案

#### 4.3.1 基于时序卷积网络（TCN）的 2D 姿态动作分类

**核心参考论文**：*Table Tennis Stroke Recognition Using Two-Dimensional Human Pose Estimation* (arXiv:2104.09907, CVPR 2021 Sports Workshop)

- **数据集**：自建数据集，14 名专业运动员，11 种基本击球动作，共 22,111 段视频
- **方法**：MediaPipe/OpenPose 提取 2D 关键点序列 → Temporal CNN 分类
- **精度**：验证集准确率 **99.37%**，未见运动员测试准确率 **98.72%**
- **11 种动作类别**：正手攻球、反手攻球、正手拉球、反手拉球、正手搓球、反手搓球、正手削球、反手削球、发球、正手挑球、反手挑球

> **这是原型验证阶段的黄金参考** — 方法轻量、精度高、可直接复用。

#### 4.3.2 基于时空双流 CNN（Twin Spatio-Temporal CNN + 3D Attention）

**核心参考论文**：*3D attention mechanism for fine-grained classification of table tennis strokes using a Twin Spatio-Temporal Convolutional Neural Networks* (arXiv:2012.05342, ICPR 2020)

- **方法**：双流网络分别处理 RGB 图像和光流图，3D 卷积 + 3D 注意力模块
- **数据集**：TTSTROKE-21（MediaEval Challenge 2020）
- **精度**：RGB + 光流组合达 **90.7%** 准确率
- **适用性评估**：⭐⭐⭐ — 精度略低于 TCN 方案，但使用原始图像而非关键点，信息更丰富

#### 4.3.3 基于改进 C3D + DensePose

- 使用 DensePose 提取人体形态 → 改进 C3D 网络学习时空特征
- **5 类分类**：正手击球、反手击球、正手拉球、反手拉球、非击球
- 优势：对光线、环境干扰具有较好鲁棒性
- **适用性评估**：⭐⭐⭐ — DensePose 部署复杂

#### 4.3.4 2D 关键点事件检测

**参考论文**：*Event Detection in Table Tennis Videos using 2D Keypoints* (arXiv:2610.08286)

- 直接使用 2D 关键点检测乒乓球比赛中的事件
- **适用性评估**：⭐⭐⭐⭐ — 方法简洁，直接以关键点为输入

### 4.4 推荐技术路线

**推荐方案：MediaPipe Pose + Temporal CNN（两阶段）**

```
阶段 1：姿态提取
    视频帧 → MediaPipe Pose → 33 关键点坐标序列
                              ↓
阶段 2：动作分类
    关键点序列 → 滑动窗口 (如 30 帧)
                ↓
    Temporal CNN (1D Conv + ReLU + MaxPool × N 层)
                ↓
    全连接层 → Softmax
                ↓
    动作分类：{正手攻, 反手攻, 正手拉, 反手拉, 发球, 搓球, ...}
```

**关键设计**：
- 滑动窗口长度：30 帧（1 秒 @ 30fps），覆盖一个完整击球动作
- 窗口步长：5-10 帧，实现重叠检测提高召回
- 输入特征：关键点坐标 (x, y) + 置信度，可选加入关节角度
- 输出类别：建议原型阶段先分 5-6 类（正手攻、反手攻、正手拉、反手拉、发球、其他），后续扩展到 11 类

## 五、球速估算

### 5.1 技术原理

球速 = 帧间真实位移 / 帧间时间间隔

$$v = \frac{\sqrt{(x_{t+1} - x_t)^2 + (y_{t+1} - y_t)^2}}{\Delta t}$$

其中 $(x, y)$ 为球在球台真实坐标系中的位置（米），$\Delta t = 1/fps$（秒）。

### 5.2 关键前提

球速估算的准确性高度依赖以下前提：

| 前提 | 要求 | 验证方法 |
|------|------|---------|
| 球的真实坐标 | 需要精确的单应性矩阵 H | 球台关键点检测精度 |
| 帧间位移 | 需要连续帧球位置检测成功 | 球体检测召回率 |
| 帧率准确 | 视频帧率需与实际一致（30fps/60fps/120fps） | FFmpeg 探测 |
| 时间基准 | 需知道帧间隔的精确值 | 1/fps |

### 5.3 难点与解决方案

#### 5.3.1 运动模糊导致的位置不确定性

高速运动下，球在单帧中呈现为模糊条纹，精确球心位置难以确定。

- **BlurBall 方案**（arXiv:2509.18387）：联合估计球位置和模糊核，从模糊条纹中恢复精确球心
- **多帧平均方案**：取连续 3-5 帧的检测位置做线性拟合，拟合斜率即为速度，可平滑单帧噪声

#### 5.3.2 30fps 帧率下的位移过大

30fps 下，球速 20m/s 时帧间位移约 0.67m，占球台长度(2.74m)的 24%。

- **问题**：线性插值假设在高速运动下可能不成立（球在弹跳后速度方向突变）
- **解决**：弹跳前/弹跳后分段计算速度；利用物理模型（抛物线）拟合轨迹

#### 5.3.3 深度方向信息缺失

单目相机无法直接获取深度信息，球在 Z 方向（远离/靠近相机）的运动会影响真实速度估算。

- **近似方案**：假设球在球台平面附近运动（实际乒乓球大部分时间确实在球台上方 0-30cm 范围内），使用 2D 球台坐标近似
- **高精度方案**：多摄像头三角测量（成本高，不适合 C 端产品）

#### 5.3.4 镜头标定（手机拍摄场景）

用户使用手机拍摄时，相机参数未知，需要：

1. **畸变校正**：手机广角镜头存在桶形畸变，需通过棋盘格标定或使用已知球台几何进行自标定
2. **自标定方案**：利用球台四角的已知真实尺寸，通过单应性矩阵间接标定相机参数
3. **简化方案**：原型验证阶段可假设无畸变（中焦段拍摄畸变较小），后续产品化阶段再增加标定流程

### 5.4 推荐技术路线

```
连续球轨迹（像素坐标）
    ↓
单应性矩阵 H → 转换为真实坐标轨迹
    ↓
弹跳事件检测 → 分段轨迹（弹跳前 / 弹跳后）
    ↓
分段线性拟合 → 速度向量 (vx, vy)
    ↓
速度大小 = √(vx² + vy²) [m/s]
    ↓
[校准] 与已知球速范围 (5-35 m/s) 对比，异常值剔除
    ↓
球速报告
```

**参数建议**：
- 拟合窗口：弹跳前/后各取 3-5 个连续检测点
- 异常值阈值：> 40 m/s 或 < 2 m/s 视为异常
- 平滑滤波：对连续多个速度值做中值滤波

## 七、验证方案设计

### 7.1 验证目标

验证"用 AI 自动分析乒乓球视频，提取球速、落点、技术动作数据"这一技术路线的整体可行性，输出各模块的技术指标数据，为产品决策提供依据。

### 7.2 验证步骤（分 5 步）

#### 步骤 1：球体检测验证（第 1-2 周）

**验证目标**：验证 TTNet/YOLO 能否在用户拍摄场景下有效检测乒乓球

**需要的数据和工具**：
- 数据：
  - OpenTTGames 数据集（38,752 训练样本，120fps 乒乓球比赛视频，含球位置标注）
  - 自采集数据：用手机（1080p/30fps）拍摄 5-10 段乒乓球训练视频（不同角度、不同光照、不同球色）
  - 自标注：人工标注 500-1000 帧的球位置作为 ground truth
- 模型：
  - TTNet（预训练权重，GitHub: maudzung/TTNet-Real-time-Analysis-System-for-Table-Tennis-Pytorch）
  - YOLO11n（使用 OpenTTGames 子集微调，Ultralytics 框架）
- 硬件：
  - 本地 GPU（RTX 3060/4060 即可）或云 T4 实例
- 评估指标：
  - 检测召回率（Recall）：成功检测到球的帧数 / 总有球帧数
  - 精确率（Precision）：正确检测数 / 总检测数
  - 平均精度（AP）：精度-召回曲线下面积
  - 处理速度：FPS

**成功标准**：
| 指标 | 目标 | 说明 |
|------|------|------|
| 检测召回率 | > 70% | OpenTTGames 测试集 |
| 检测精确率 | > 80% | 误检率控制在 20% 以内 |
| 处理速度 | > 10 FPS | T4 GPU 上 |
| 自采集视频召回率 | > 50% | 用户场景泛化能力 |

**操作步骤**：
1. 下载 OpenTTGames 数据集，按训练/验证/测试集划分
2. 克隆 TTNet 仓库，按 README 配置环境，加载预训练权重
3. 在测试集上运行评估，记录 Recall/Precision
4. 使用 OpenTTGames 子集（球检测标注）微调 YOLO11n
5. 在自采集视频上测试 TTNet 和 YOLO11n，对比性能
6. 分析失败案例（遮挡？模糊？背景干扰？），记录改进方向

#### 步骤 2：球台检测与坐标映射验证（第 2-3 周，与步骤 1 并行）

**验证目标**：验证从画面中检测球台四角并建立坐标映射的准确性

**需要的数据和工具**：
- 数据：
  - 自采集视频（步骤 1 同一批），人工标注球台四角位置
  - OpenTTGames 球台语义分割掩码
- 模型/算法：
  - YOLOv8-pose（关键点检测，标注球台 6 关键点微调）
  - OpenCV `findHomography` + `perspectiveTransform`
- 硬件：本地 GPU 或云 T4

**成功标准**：
| 指标 | 目标 | 说明 |
|------|------|------|
| 球台关键点检测误差 | < 10 像素 | 平均欧氏距离 |
| 坐标映射误差 | < 15cm | 真实坐标系中的落点误差 |
| 球台检测成功率 | > 90% | 不同角度/光照条件下 |

**操作步骤**：
1. 人工标注 100 张图片的球台 6 个关键点
2. 训练 YOLOv8-pose 模型（预训练 COCO 权重 → 乒乓球球台微调）
3. 在测试图片上评估关键点检测精度
4. 使用 OpenCV 计算单应性矩阵 H
5. 将已知球位置（标注数据）通过 H 映射到真实坐标，对比与真实物理位置误差
6. 验证不同拍摄角度下的映射精度

#### 步骤 3：姿态估计与动作识别验证（第 3-4 周）

**验证目标**：验证 MediaPipe + Temporal CNN 能否正确识别击球动作类型

**需要的数据和工具**：
- 数据：
  - 自采集视频：录制 5-10 种击球动作各 20-30 次（正手攻、反手攻、正手拉、反手拉、发球、搓球）
  - 公开数据集：参考 arXiv:2104.09907 的方法（11 类动作，22,111 段视频），如可获取
- 模型/工具：
  - MediaPipe Pose（`mediapipe` Python 包，BlazePose 模型）
  - Temporal CNN：参考 arXiv:2104.09907 的网络结构
  - PyTorch 框架
- 硬件：CPU 即可运行 MediaPipe，训练 TCN 需 GPU

**成功标准**：
| 指标 | 目标 | 说明 |
|------|------|------|
| 动作分类准确率 | > 80% | 6 类动作分类 |
| 动作检测召回率 | > 70% | 击球事件是否被检出 |
| 姿态估计 FPS | > 20 FPS | CPU 上运行 |
| 未见运动员准确率 | > 60% | 泛化能力 |

**操作步骤**：
1. 使用 MediaPipe Pose 提取视频中的关键点序列
2. 按击球事件切分视频片段（可手动标注或使用球检测的击球时间戳）
3. 标注每个片段的击球动作类型（6 类）
4. 构建 Temporal CNN 模型（3-5 层 1D Conv + 全连接）
5. 训练并评估，记录准确率/召回率/F1
6. 测试未见运动员的动作识别准确率

#### 步骤 4：球速与落点估算验证（第 4-5 周）

**验证目标**：验证从视频轨迹到球速和落点的端到端估算精度

**需要的数据和工具**：
- 数据：步骤 1-3 的输出（球轨迹 + 单应性矩阵 + 弹跳事件）
- 真实球速参考：使用发球机（固定速度档位）或雷达测速仪获取真实球速
- 算法：OpenCV（坐标变换）、NumPy（线性拟合）

**成功标准**：
| 指标 | 目标 | 说明 |
|------|------|------|
| 球速估算误差 | < 30% | 与真实球速对比 |
| 落点准确率 | > 60% | 落在正确的 6 区域之一 |
| 弹跳检测成功率 | > 70% | 弹跳事件检出 |

**操作步骤**：
1. 使用发球机以已知速度发球，同时用手机录像
2. 运行完整的球检测 → 追踪 → 坐标映射 → 速度计算流水线
3. 对比估算球速与已知球速，计算误差率
4. 标注 50-100 个实际落点位置，对比系统估算落点，计算区域准确率
5. 分析误差来源（球检测精度？单应性矩阵精度？帧率不足？）

#### 步骤 5：端到端集成验证（第 5-6 周）

**验证目标**：完整流水线集成测试，验证端到端处理一段视频的整体效果

**需要的数据和工具**：
- 10-20 段用户场景视频（手机拍摄，不同角度/光照/水平）
- 完整的 AI 分析流水线（部署在云 GPU 上）
- 前端展示界面（简单 Web 页面展示分析报告）

**成功标准**：
| 指标 | 目标 | 说明 |
|------|------|------|
| 端到端处理成功率 | > 80% | 10 段视频中至少 8 段成功输出报告 |
| 单视频处理时间 | < 5 分钟 | 3 分钟视频在 GPU 上 |
| 报告内容完整度 | > 70% | 包含球速/落点/动作/轨迹四项 |
| 用户主观满意度 | "基本可用" | 教练/运动员主观评价 |

**操作步骤**：
1. 整合步骤 1-4 的模块为完整流水线
2. 部署到云 GPU 实例（T4 或 A10）
3. 准备 10-20 段测试视频
4. 批量处理，记录每段视频的处理结果和耗时
5. 生成分析报告（球速统计、落点热力图、动作分布、轨迹可视化）
6. 邀请 1-2 位乒乓球教练/运动员评估报告的可用性
7. 汇总各模块指标，输出验证结论

### 7.4 风险点与备选方案

| 风险点 | 风险描述 | 概率 | 影响 | 备选方案 |
|--------|---------|------|------|---------|
| 球检测召回率不达标 | 30fps 下运动模糊严重，TTNet 迁移到 30fps 可能性能下降 | 中 | 高 | 使用 TrackNetV2/V4 在自采集数据上迁移学习；提升帧率到 60fps（用慢动作录制模拟） |
| 用户手机拍摄角度过大 | 侧拍角度导致球台关键点遮挡，单应性矩阵不准确 | 中 | 高 | 增加自标定容错；限制推荐拍摄角度（球台侧后方 45°）；使用多帧关键点检测取平均 |
| 动作识别类别过少 | 原型阶段只分 6 类，无法满足实际分析需求 | 低 | 中 | 采用渐进式扩展策略，先验证 6 类可行性，后续逐步增加到 11+ 类 |
| 球速估算误差过大 | 30fps 帧间位移大 + 单目深度缺失，速度估算可能偏差 30%+ | 高 | 中 | 使用抛物线物理模型拟合替代线性拟合；增加多帧平滑；提供速度范围而非精确值 |
| 云 GPU 成本超预算 | 按量付费在调试阶段可能频繁使用 | 中 | 低 | 使用抢占式实例降低成本；本地 GPU 完成调试后仅在云端做验证测试 |
| 自采集数据标注量不足 | 人工标注耗时，500-1000 帧可能不够训练 | 高 | 中 | 使用半自动标注（先用 TTNet 预标注，人工修正）；利用 OpenTTGames 已有标注减少标注量 |
| 模型泛化到 C 端用户场景失败 | 比赛视频（固定机位、120fps）与手机拍摄（手持、30fps）差异大 | 高 | 高 | 在原型阶段就使用手机采集数据进行验证；数据增强（模拟运动模糊、角度变化） |

## 结论与技术可行性判断

基于以上系统性调研，对"乒乓球视频 AI 分析"技术可行性形成以下判断：

### 整体可行性：✅ 可行（有条件）

乒乓球视频 AI 分析的技术路线在学术界已有充分验证，关键模块均有可复用的开源代码和公开数据集。但"实验室场景可行"与"C 端用户手机拍摄场景可行"之间存在显著 gap，需通过原型验证来评估泛化能力。

### 各模块可行性评估

| 模块 | 可行性 | 置信度 | 关键依赖 |
|------|--------|--------|---------|
| 球体检测 | ✅ 可行 | 高 | TTNet 架构成熟，但需验证 30fps 手机视频泛化 |
| 球体追踪 | ✅ 可行 | 中高 | 卡尔曼滤波 + 物理模型方案成熟 |
| 球台检测 | ✅ 可行 | 高 | YOLO-pose + OpenCV 单应性矩阵方案标准化 |
| 坐标映射 | ✅ 可行 | 高 | 单应性矩阵方法成熟 |
| 动作识别 | ✅ 可行 | 高 | 2D 姿态 + TCN 方案达 99.37% 准确率（有论文验证） |
| 球速估算 | ⚠️ 有条件可行 | 中 | 30fps + 单目相机限制大，误差可能 20-30% |
| 落点估算 | ⚠️ 有条件可行 | 中 | 依赖球检测和坐标映射的级联精度 |
| 云 GPU 推理 | ✅ 可行 | 高 | T4/A10 实例成本低，流水线架构标准 |

### 核心风险

1. **最大风险**：30fps 手机拍摄场景下球检测的召回率和精度（所有下游模块都依赖此）
2. **次大风险**：用户拍摄角度多样性导致球台关键点检测不稳定
3. **可控风险**：球速估算精度（可通过提供速度范围、多帧平滑等方法缓解）

### 建议下一步行动

1. 立即启动步骤 1（球体检测验证），这是整个方案的瓶颈模块
2. 并行启动步骤 2（球台检测），两者无依赖
3. 采集测试数据时，优先使用手机 + 三脚架固定机位拍摄（降低变量）
4. 与 1-2 位乒乓球教练建立沟通，确保输出指标符合实际训练需求
