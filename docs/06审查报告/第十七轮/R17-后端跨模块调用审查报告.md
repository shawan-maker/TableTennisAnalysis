## 4. WebSocket 事件字段一致性验证

### 4.1 项目约定

notification 模块 `_push_ws` 方法（L382）定义 WS 消息格式：
```python
message = json.dumps({"event": event, "data": data})
```

项目所有通过 `push_ws_message` 推送的 WS 消息使用 `"event"` 作为消息类型字段名。前端 WS 处理器（如 scoring frontend L1390 `msg.event === 'match_finished'`）统一检查 `"event"` 字段。

### 4.2 各模块 WS 推送字段使用

| 模块 | 推送方式 | 字段名 | 消息类型 | 验证 |
|------|----------|--------|----------|------|
| scoring | `ws_manager.broadcast_to_room` L803 | **"type"** | score_update | ❌ P1 |
| scoring | `ws_manager.broadcast_to_room` L890 | **"type"** | score_update（undo） | ❌ P1 |
| scoring | `push_ws_message` L974 | "event" | match_finished | ✅ |

### 4.3 不一致性分析

scoring 模块在实时记分场景（`broadcast_to_room`）使用 `"type": "score_update"`，与项目约定的 `"event"` 字段名不一致。虽然 `broadcast_to_room` 和 `push_ws_message` 使用不同的 Redis channel（`ws:match:{match_id}` vs `ws:user:{user_id}`），但前端 WS 消息解析器需要同时处理 `"type"` 和 `"event"` 两种字段名，违反协议一致性。

## 6. 新发现问题详情

### P0-1：ai_pipeline `_trigger_cascade` send_task 参数与任务定义签名不匹配

**文件**：`13-infrastructure/ai_pipeline.md` L792-799 + `07-training_advice/backend.md` L1131-1132 + `08-progress_analysis/backend.md` L1328-1329

**问题**：

ai_pipeline `_trigger_cascade` 方法（L784 `async def _trigger_cascade(task_id: int, report_id: int, user_id: int)`）通过 `celery_app.send_task` 调用外部模块任务时，传递的参数数量与任务定义的参数数量不匹配：

```python
# ai_pipeline L792-794 — 传递 1 个参数
celery_app.send_task(
    "training_advice.generate_advice",
    args=[report_id],           # ← 仅 1 个 arg
)

# ai_pipeline L797-799 — 传递 1 个参数
celery_app.send_task(
    "progress_analysis.generate_snapshot",
    args=[report_id],           # ← 仅 1 个 arg
)
```

但任务定义期望 2 个参数：

```python
# training_advice L1131-1132 — 期望 2 个参数
@celery_app.task(name="training_advice.generate_advice")
def generate_advice_task(user_id: int, report_id: int):  # ← 2 个参数

# progress_analysis L1328-1329 — 期望 2 个参数
@celery_app.task(name="progress_analysis.generate_snapshot")
def generate_snapshot_task(user_id: int, report_id: int):  # ← 2 个参数
```

`send_task` 将 `args=[report_id]` 发送到 Celery broker，worker 接收后调用 `generate_advice_task(report_id)` — 此时 `user_id=report_id`，而 `report_id` 参数缺失，触发：

```
TypeError: generate_advice_task() missing 1 required positional argument: 'report_id'
```

**影响**：严重 — AI 分析完成后，训练建议生成（training_advice）和进度快照生成（progress_analysis）均会失败。用户完成视频分析后无法获得训练建议和进度追踪。虽然 `send_task` 本身不会抛异常（仅入队），但 worker 端执行必失败。

**修复建议**：

`_trigger_cascade` 方法已有 `user_id` 参数可用，修改 2 处 send_task 的 args：

```python
# L792-794
celery_app.send_task(
    "training_advice.generate_advice",
    args=[user_id, report_id],   # ← 添加 user_id
)

# L797-799
celery_app.send_task(
    "progress_analysis.generate_snapshot",
    args=[user_id, report_id],   # ← 添加 user_id
)
```

### P1-1：scoring 模块 WS 广播使用 `"type"` 字段而非项目约定的 `"event"`

**文件**：`04-scoring/backend.md` L803, L890

**问题**：

scoring 模块实时记分通过 `ws_manager.broadcast_to_room` 推送 WS 消息时，使用 `"type"` 作为消息类型字段名：

```python
# L800-813
await ws_manager.broadcast_to_room(
    f"ws:match:{match_id}",
    json.dumps({
        "type": "score_update",    # ← 使用 "type"
        "data": { ... }
    }),
)

# L887-898
await ws_manager.broadcast_to_room(
    f"ws:match:{match_id}",
    json.dumps({
        "type": "score_update",    # ← 使用 "type"（undo 场景）
        "data": { ... }
    }),
)
```

项目所有通过 `NotificationService.push_ws_message` 推送的 WS 消息使用 `"event"` 字段（notification L382 `json.dumps({"event": event, "data": data})`）。前端 WS 处理器统一检查 `msg.event`（如 scoring frontend L1390 `msg.event === 'match_finished'`）。

scoring 的 `broadcast_to_room` 使用 `"type"` 字段，前端需要为 match room channel 编写独立的解析逻辑检查 `msg.type`，与 user notification channel 的 `msg.event` 解析逻辑不一致。

**影响**：中 — 不会导致功能完全失败（前端可为 match room channel 编写独立解析器），但违反项目 WS 协议一致性。若前端使用统一 WS 解析器，scoring 实时记分消息将无法被识别。

**修复建议**：将 L803 和 L890 的 `"type": "score_update"` 改为 `"event": "score_update"`，与项目约定一致。

### P1-2：file_management 和 ai_inference 的 4 个 Celery 任务使用 `async def` 而非 `def` + `asyncio.run()`

**文件**：
- `13-infrastructure/file_management.md` L495-496, L510-511
- `13-infrastructure/ai_inference.md` L702-703, L745

**问题**：

4 个 Celery 任务使用 `async def` 声明，与项目标准模式 `def` + `asyncio.run()` 不一致：

```python
# file_management L495-496
@celery_app.task(name="file_management.cleanup_orphans")
async def cleanup_orphan_files():     # ← async def

# file_management L510-511
@celery_app.task(name="file_management.physical_delete")
async def physical_delete_task(...):  # ← async def

# ai_inference L702-703
@celery_app.task(name="ai_inference.health_check")
async def check_inference_health():    # ← async def

# ai_inference L745
@celery_app.task(name="ai_inference.check_available")
async def is_inference_available():   # ← async def
```

项目标准（notification L868 注释）明确："Celery worker 默认不支持 async def task，使用 asyncio.run() 驱动异步逻辑。" 其余 9 个 Beat 任务（notification/admin/ai_pipeline/gamification/user/membership/scoring）均使用 `def` + `asyncio.run()` 模式。

`async def` 的 Celery task 在默认 prefork worker 下，函数返回的 coroutine 不会被 await，导致任务实际逻辑不执行。

**影响**：中 — 4 个任务中 3 个为 Beat 定时任务（cleanup_orphans / health_check / physical_delete），1 个为按需任务（check_available）。Beat 任务会按时触发但 worker 端不执行实际逻辑，导致孤儿文件清理和 GPU 健康检查静默失效。

**修复建议**：将 4 个任务改为 `def` + `asyncio.run()` 模式：

```python
# file_management
@celery_app.task(name="file_management.cleanup_orphans")
def cleanup_orphan_files():
    import asyncio
    asyncio.run(FileService.cleanup_orphan_files())

@celery_app.task(name="file_management.physical_delete")
def physical_delete_task(file_id: int, oss_key: str):
    import asyncio
    asyncio.run(FileService.physical_delete_oss_object(file_id, oss_key))

# ai_inference
@celery_app.task(name="ai_inference.health_check")
def check_inference_health():
    import asyncio
    asyncio.run(_check_inference_health_async())

@celery_app.task(name="ai_inference.check_available")
def is_inference_available() -> bool:
    import asyncio
    return asyncio.run(_is_inference_available_async())
```

### P2-1：file_management `archive_for_training` 使用未定义的 `async_db_session`

**问题**：
