## 4. 新发现问题详情

### P3-1：create_share 积分 ref_id 使用 report_id 而非 share.id

**文件**：`03-video_analysis/backend.md` L1061

**问题**：`create_share` 方法 L1061 调用积分：

```python
await GamificationService.add_points(db, user_id=user_id, event_type="share", ref_id=report_id)
```

`ref_id` 传入的是 `report_id`（被分享的报告 ID），而非新创建的 `share.id`（分享记录 ID）。

**对比其他积分链**：
- match 积分：`ref_id=match_id`（业务实体 ID）✅
- record 积分：`ref_id=record.id`（业务实体 ID）✅
- feedback 积分：`ref_id=feedback_id`（业务实体 ID）✅
- analysis 积分：`ref_id=report_id`（业务实体 ID）✅

share 积分的业务实体是 ShareRecord，但 `ref_id` 传入的是被分享的 AnalysisReport 的 ID，而非 ShareRecord 的 ID。这导致：
1. 同一报告被多次分享时，所有积分记录的 `ref_id` 相同，无法区分不同分享
2. 审计追溯无法从积分记录定位到具体的 ShareRecord

**影响**：低 — 积分触发正常，不影响功能正确性。仅影响审计粒度。

**修复建议**：将 L1061 改为：
```python
await GamificationService.add_points(db, user_id=user_id, event_type="share", ref_id=share.id)
```

注意：`share` 在 L1048 定义，L1056 `db.commit()` 后已刷新含 `share.id`。

### P3-2：create_share 和 submit_feedback 中 add_points 后冗余 db.commit()

**文件**：`03-video_analysis/backend.md` L1062, L928

**问题**：

create_share L1059-1064：
```python
try:
    from app.services.gamification_service import GamificationService
    await GamificationService.add_points(db, user_id=user_id, event_type="share", ref_id=report_id)
    await db.commit()  ① ← 冗余
except Exception as e:
    logger.error(...)
```

submit_feedback L925-930：
```python
try:
    from app.services.gamification_service import GamificationService
    await GamificationService.add_points(db, user_id=user_id, event_type="feedback", ref_id=feedback_id)
    await db.commit()  ① ← 冗余
except Exception as e:
    logger.error(...)
```

`GamificationService.add_points` L567-590 内部已执行 `db.commit()`（L583）。调用方在 `add_points` 之后再执行 `db.commit()` 是空操作（无 pending session changes），不会导致错误，但产生无用的数据库往返。

**对比**：scoring `finish_match`、match_data `_trigger_gamification`、ai_pipeline `_trigger_cascade` 在 `add_points` 之后均**无**冗余 `db.commit()`，仅用 try-except 包裹。
