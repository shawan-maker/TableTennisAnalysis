## 4. quota Redis Key 时区一致性 ⚠️

### P1-TZ-01：quota Redis Key 日期计算时区不一致

第十三轮修复了日期**格式**不一致（`strftime` → `isoformat`），但日期**时区基准**仍不一致：

| 模块 | 文件+行号 | 时区基准 | 日期计算 |
|------|----------|----------|----------|
| video_analysis | `03-video_analysis/backend.md` L657-660 | 显式 CST (UTC+8) | `datetime.now(tz_cst).date().isoformat()` |
| membership | `10-membership/backend.md` L548-550 | 服务器本地时区 | `date.today().isoformat()` |
| membership | `10-membership/backend.md` L636 | 服务器本地时区 | `date.today()` |
| ai_pipeline | `13-infrastructure/ai_pipeline.md` L869-870 | 服务器本地时区 | `date.today().isoformat()` |

**影响**：当服务器时区不为 UTC+8 时（如 Docker 默认 UTC），同一时刻 video_analysis 的 `_check_free_quota`（写）和 membership 的 `consume_analysis_quota`（读/写）或 ai_pipeline 的 `refund_free_quota`（退还）可能命中不同的 Key，导致额度计数断裂。

**与前序轮次差异**：第十三轮 P1-REDIS-01 修复的是日期格式（`20261015` vs `2026-10-15`），本轮发现的是时区基准不一致（CST vs 系统时区），是同一问题更深层次的表现。

### P2-DEAD-01：consume_analysis_quota 为死代码

`10-membership/backend.md` L528-564 `MembershipService.consume_analysis_quota` 方法文档注释"由 video_analysis 模块 POST /video-analysis/tasks 时调用"，但实际 video_analysis `create_task` 调用的是自身的 `_check_free_quota` 方法，未调用 `consume_analysis_quota`。

存在两套独立的额度管理实现（video_analysis 的 `_check_free_quota` 和 membership 的 `consume_analysis_quota`），逻辑重复且时区计算不一致（参见 P1-TZ-01）。
