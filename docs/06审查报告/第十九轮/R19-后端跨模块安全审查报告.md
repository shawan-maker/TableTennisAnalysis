## 6. 业务链路完整性

### 6.1 AI 流水线 10 步 cascade

```
group(step_1_preprocess, step_2_table_detect) 
  | chain(step_3_ball_detect → step_4_ball_track → step_5_landing)
  + chain(step_6_pose → step_7_action → step_8_rally)
  | join → chain(step_9_report → step_10_annotated_video)
  | _trigger_cascade → send_task(training_advice.generate_advice)
                     → send_task(progress_analysis.generate_snapshot)
                     → send_task(dashboard.bust_cache)
```

- **熔断器**：`AICircuitBreaker`（`ai_pipeline.md` L940-988）—— 5 次失败后 open 状态 120s，half_open 状态 120s 探测；调用前 `is_call_allowed` 检查；调用失败 `record_failure` 累加；调用成功 `record_success` 重置。
- **回退**：熔断 open 时 `raise AppException("AI 推理服务暂时不可用（熔断中）", 503)`，由上层统一处理。

**结论**：AI 流水线 10 步 cascade + 熔断器 + 级联触发完整无缺。

### 6.2 微信支付 9 环节链路

```
1. create_order → 2. sign_order → 3. wechat_unifiedorder → 4. user_pay
→ 5. wechat_callback → 6. verify_sign → 7. decrypt_callback
→ 8. process_business → 9. push_notification
```

- **幂等**：`handle_notify` 通过订单状态 + transaction_id 双重校验
- **退款**：`refund` 7 天限制 + 金额校验 + 状态校验
- **续期**：`subscription` 续期 + `quota:bonus` Redis incrby + 90d TTL
- **审计**：所有支付操作写入 `audit_log`（action: `payment_order_created` / `payment_callback_processed` / `payment_refunded` / `subscription_created_or_renewed`）

**结论**：微信支付 9 环节链路完整。

### 6.3 账号注销 8 步链路

```
1. request_deletion → user.status = "pending_deletion" + scheduled_deletion_at = now + 72h
2. cancel_deletion → user.status = "active" + scheduled_deletion_at = NULL
3. process_account_deletions（Celery 每日 02:00）→ 筛选 scheduled_deletion_at < now 的用户
  3.1 user 数据匿名化（nickname/phone/openid 置 "deleted"）
  3.2 file_record 标记 deleted
  3.3 analysis_report.is_anonymized = True
  3.4 subscription.status = "cancelled"
  3.5 user.status = "deleted"
  3.6 Redis 清理 3 key（user:profile / user:big_data / ws:user）
  3.7 audit_log 记录
4. export_user_data → 生成 zip + 30 天 OSS 链接 + 月度限流
```

### 8.1 AppException vs HTTPException（通过）

grep `raise\s+(AppException|HTTPException|ValueError|Exception|PipelineError)` 命中 100+ 处：

**结论**：错误处理一致性通过，AppException 已统一覆盖业务层，无 HTTPException 残留。

### 8.2 错误码规范

- 400：请求参数错误（`文件大小与声明不符` / `未提供更新字段` / `分享不存在或已过期`）
- 401：未认证（`请重新登录` / `Token 已撤销` / `H5 Token 已过期`）
- 403：无权限（`您的账号正在注销中` / `管理员账号已禁用` / `需要超级管理员权限`）
- 404：资源不存在（`报告不存在` / `用户不存在` / `比赛不存在` / `配置 {key} 不存在`）
- 409：冲突（`您已提交注销申请` / `今日已打卡` / `比赛已开始或已结束` / `配置 {key} 已存在`）
- 422：业务校验失败（`会员等级或周期参数不合法` / `比分不符合赛制规则` / `超过 7 天的订单不可退款`）
- 429：限流（`验证码已发送，1 分钟后重试` / `今日免费分析次数已用完` / `本月已导出过，请下月再试`）
- 502：外部服务异常（`微信登录服务暂时不可用` / `支付服务暂时不可用` / `退款服务暂时不可用`）
- 503：服务不可用（`AI 推理服务暂时不可用（熔断中）` / `Ball detection model not loaded`）
- 504：超时（`Ball detection timeout` / `Pose estimation timeout`）

**结论**：错误码语义清晰，4xx 与 5xx 边界明确，便于前端统一处理。

### 8.3 model_validate 注入完整性（通过）

grep `model_validate\(|\.model_dump\(\)|from_attributes` 命中 68 处：

- 所有 Service 层返回 Schema 时使用 `Schema.model_validate(orm_obj)` 或 `Schema.model_validate(orm_obj).model_dump()`
- 所有 Brief Schema 配置 `model_config = {"from_attributes": True}`，支持从 ORM 对象直接构造
- 跨层传递使用 `model_dump()` 序列化为 dict，避免 ORM 对象泄露到 API 层

**结论**：model_validate 注入完整，无 dict 手工构造，无 ORM 对象直接返回。

### 10.3 Sentry 错误追踪

- **初始化**：`configure_sentry(sentry_dsn, environment, traces_sample_rate)` 在 `SENTRY_DSN` 为空时跳过（dev 环境不初始化）
- **集成**：FastApiIntegration / CeleryIntegration / RedisIntegration / SqlalchemyIntegration / LoggingIntegration
- **脱敏**：`before_send` 钩子脱敏 `request.data` 和 `extra` 中的 9 个敏感字段（`phone` / `token` / `access_token` / `refresh_token` / `openid` / `session_key` / `password` / `api_key` / `wechat_code` / `session_key`）
- **采样**：生产 100% ERROR 采样；WARNING 10% 采样；`traces_sample_rate=0.1` 性能事务采样
- **过滤**：`ignore_errors=["fastapi.exceptions.HTTPException", "app.core.exceptions.AppException"]` 排除 4xx 业务错误
- **手动上报**：AI 分析失败 / 微信支付验签失败 / GPU OOM 恢复失败 / Celery 重试耗尽 4 个关键场景

> **P2-A**：`sentry.configure_sentry` 中 `ignore_errors` 参数使用字符串形式 `"app.core.exceptions.AppException"`（`sentry.md` L92-95）。Sentry SDK 5.x+ 版本对 `ignore_errors` 的字符串匹配行为已废弃，推荐使用异常类对象。若 SDK 升级到 6.x+，字符串匹配可能失效，导致 4xx 业务错误被误报到 Sentry。
>
> **修复建议**：改为异常类对象列表 `[HTTPException, AppException]`，或在 `before_send` 钩子中通过 `hint["exc_info"][0]` 判断异常类型主动过滤。

### 10.4 三件套协同设计

- **request_id 关联**：structlog 的 `request_id` 与 Sentry 的 `set_tag("request_id", ...)` 一致，可通过 `request_id` 在日志和 Sentry 之间交叉查询
- **5xx 上报策略**：AppException status_code >= 500 → Sentry `capture_exception`；4xx 仅 structlog WARNING，不上报
- **未捕获异常**：`unhandled_exception_handler` 记录 ERROR 日志 + 上报 Sentry + 返回 500 通用错误

**结论**：监控三件套协同设计完整，覆盖日志 / 指标 / 错误追踪三个维度，request_id 贯穿全链路。
