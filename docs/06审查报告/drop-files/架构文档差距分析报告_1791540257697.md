## 二、关键缺失（🔴 必须补充）

### 2.1 缺少数据库 ER 图 / 表结构设计

**现状**：模块矩阵列出了核心实体名称（如 User, VideoTask, Match, Post, Tournament, Equipment, CreditScore 等），但全文无任何 ER 图、表结构定义或关系说明。

**影响**：
- 无法判断实体间关系是否合理（如 User→VideoTask 是 1:N，Match→ScoreRecord 是 1:N，Post→Comment 是 1:N）
- JSONB 存储分析结果的结构虽有示例（第 6.3 节），但知识库、规则引擎、训练方案等 JSONB 结构未定义
- PostgreSQL 表分区策略未提及（video_task 表随用户增长会很大）

**建议**：
- 至少补充 Phase 1 核心实体的高层 ER 图（Mermaid erDiagram）
- 标注关键关系基数（1:1, 1:N, M:N）
- 说明 JSONB 字段的存储策略和查询方式
- 对高增长表（video_task, score_record, post）提出分区/归档策略

### 2.2 缺少 API 端点设计

**现状**：定义了 REST 统一格式（`/api/v1/{module}/{resource}`）和响应结构（`{code, message, data, timestamp}`），但全文未列出任何具体 API 端点。

**影响**：
- 前端无法对照后端 API 进行开发
- 模块间接口边界不清晰（如 video_analysis 模块暴露哪些端点给前端和给 Celery）
- WebSocket 事件类型有列举但 REST 端点完全没有

**建议**：
- 至少补充 Phase 1 核心模块的 API 端点清单（HTTP Method + Path + 简述 + 权限）
- 可按模块分组，每个模块 5-10 个核心端点
- 标注哪些端点需要会员权限、哪些需要限流

### 2.3 "乒乓大数据"间接胜利算法未设计

**现状**：前端设计 P5.1 和需求 v0.4 模块 2 都明确要求"乒乓大数据"功能，包含"间接战胜马龙/孙颖莎"趣味数据。架构文档 user 模块职责中提及"乒乓大数据"但未描述实现方案。

**问题**："间接战胜"是一个图遍历问题——A 战胜 B，B 战胜 C，则 A 间接战胜 C。随用户量增长，全图 BFS/DFS 计算成本极高。

**建议**：
- 设计预计算 + 缓存策略：比赛结束后异步更新关联用户的间接胜利集合
- 限制遍历深度（如最多 3-4 层）
- 使用 Redis 缓存计算结果，TTL 设为 24h
- 在 user 模块下明确 `big_data_stats` 子模块及其计算触发机制

### 2.4 视频转码策略缺失

**现状**：AI 流水线 Step 1 提到"FFmpeg 转码/抽帧"，但用户上传的视频可能是不同格式（mp4/mov/avi）、不同分辨率（720p/1080p/4K）、不同帧率（24/30/60fps）。

**缺失内容**：
- 用户上传后的标准化转码策略（统一转为什么格式/分辨率/帧率再送入 AI）
- 多清晰度输出策略（CDN 分发需要 1080p/720p/480p 多版本）
- 视频缩略图/封面图生成
- 转码任务与 AI 分析任务的编排关系（先转码再分析？还是并行？）

**建议**：
- 在 file_management 模块下补充视频转码子流程
- 定义标准化输入格式（如统一 30fps 1080p H.264 mp4）
- 转码与 AI Step 1 可合并，但多清晰度输出应作为独立异步任务
- 定义转码超时和失败降级策略

### 2.5 通知分发策略不完整

**现状**：notification 模块列出 WebSocket 推送和微信模板消息，但未说明何时用哪种通道。

**缺失内容**：
- 通道选择规则：在线用户用 WebSocket，离线用户用微信订阅消息/模板消息，紧急通知用 SMS
- 微信订阅消息需用户主动订阅（一次性订阅 vs 长期订阅），架构未描述订阅管理
- 训练提醒的触发机制（定时任务？基于上次分析时间的规则？）
- 通知优先级和频率控制（避免骚扰用户）

**建议**：
- 补充通知分发策略矩阵：通知类型 × 用户在线状态 × 通道选择
- 在 notification 模块下增加 `subscription_manager`（微信订阅消息状态管理）
- 定义定时通知的 Celery beat 任务（如每日训练提醒）

### 2.6 AI 服务熔断/降级机制缺失

**现状**：AI 流水线提到超时控制（600s）和重试策略（2 次指数退避），但未设计熔断器模式和降级策略。

**风险场景**：
- GPU 实例不可用/被回收（Spot 实例可能被抢占）
- AI 推理服务 OOM 或模型加载失败
- LLM API 不可用或超时

**缺失内容**：
- 熔断器模式：连续 N 次失败后熔断，避免雪崩
- Spot 实例被抢占后的任务重排队策略
- LLM 不可用时的降级方案（文档提到"降级为纯规则引擎输出"但未设计切换逻辑）
- 用户侧的体验降级（如"分析服务繁忙，稍后查看结果"）

**建议**：
- 在 ai_pipeline 模块下增加 `circuit_breaker` 设计
- Spot 实例抢占检测 + 任务自动重排队
- LLM 降级开关设计（环境变量控制，失败自动切换规则引擎）

### 2.7 数据隐私与合规（PIPL）未覆盖

**现状**：安全规范第 10.3 节提到"视频隐私""敏感字段脱敏"，但未覆盖《个人信息保护法》(PIPL) 合规要求。

**缺失内容**：
- 用户数据留存策略（原始视频留存多久？分析结果留存多久？）
- 用户注销账号后的数据删除流程（"被遗忘权"）
- 用户数据导出功能（PIPL 要求的可携带权）
- 隐私政策和用户授权流程设计
- 敏感数据（手机号、位置信息）的加密存储

**建议**：
- 增加数据合规章节
- 定义数据留存/清理策略（如原始视频 90 天后转冷存储，1 年后删除）
- 在 user 模块增加 `account_deletion` 流程
- 在 admin 模块增加数据导出工具

## 三、规格不足（🟡 应展开）

### 3.1 搜索服务架构未设计

**现状**：前端设计有大量搜索场景（社区搜索、视频搜索、球馆搜索、装备搜索、赛事搜索），架构文档 Phase 3 扩展点提到"搜索引擎"但未设计。

**建议**：
- Phase 1-2 可用 PostgreSQL 全文搜索（`tsvector` + `GIN` 索引）
- Phase 3+ 评估引入 Elasticsearch 或 Meilisearch（社区内容量增长后 PG 全文搜索性能不足）
- 至少在架构文档中标注搜索方案的技术选型方向

### 3.2 内容审核流程未展开

**现状**：Phase 3 `content_moderation` 模块列出了职责（敏感词过滤、举报处理），安全规范提到"敏感词过滤+人工审核队列"，但未设计具体流程。

**缺失内容**：
- 自动审核：敏感词库来源、匹配算法、图片/视频审核方案（OCR? 第三方 API?）
- 审核队列工作流：待审 → 通过/拒绝/人工复审
- 创作者视频审核标准与时效要求
- 举报处理 SLA

**建议**：补充内容审核流程图和审核规则定义

### 3.3 智能组队算法未设计

**现状**：Phase 4 `activity` 模块提到"现场智能组队"（TeamAssignment 实体），需求 v0.4 要求"按积分智能匹配队伍，保证实力平均"。

**缺失内容**：
- 组队算法描述（如贪心算法：按积分排序后蛇形分配队伍）
- 积分来源（开球网积分）
- 算法复杂度和实时性要求（现场组队需要快速计算）

**建议**：在 activity 模块下补充组队算法设计

### 3.4 CDN 缓存策略未设计

**现状**：架构提到 CDN 用于视频/3D 模型/静态资源分发，但未设计缓存策略。

**缺失内容**：
- 缓存层级和 TTL（视频永久缓存？3D 模型版本化缓存？）
- 缓存失效策略（用户更新头像后 CDN 如何刷新？）
- CDN 回源比例和成本控制

**建议**：补充 CDN 缓存策略表

### 3.5 测试策略未设计

**现状**：目录结构有 `tests/` 目录（unit/ + integration/），但未描述测试策略。

**缺失内容**：
- 单元测试覆盖目标（建议核心模块 >80%）
- 集成测试方案（API 级别？数据库级别？）
- AI 模型评估流程（如何衡量模型精度？回归测试？）
- 前端 E2E 测试方案
- 测试数据管理（特别是 AI 模型测试需要标注数据集）

**建议**：补充测试策略章节，重点关注 AI 模型评估流程

### 3.6 监控告警细节不足

**现状**：提到"阿里云云监控/Prometheus"，但未定义关键指标和告警阈值。

**缺失内容**：
- 关键监控指标清单（API 延迟 P95/P99、GPU 利用率、队列深度、错误率、WebSocket 连接数）
- 告警阈值（如队列深度 > 10 告警、GPU 利用率 < 20% 告警）
- 个人开发者场景的值班响应策略（无人 24h on-call，需定义紧急/非紧急分级）

**建议**：补充监控指标表和告警分级

### 3.7 成本监控与预算告警缺失

**现状**：GPU 成本有估算（¥354-3000/月），LLM 成本有预算（¥0.1-0.3/次），但无成本监控设计。

**缺失内容**：
- 月度成本汇总和趋势（GPU + OSS + CDN + LLM + SMS + 地图 API）
- 预算告警（如月成本超预算 80% 告警）
- 免费用户成本控制（每日 3 次免费分析的 GPU 成本如何控制？）

**建议**：在 admin 模块增加成本看板设计

### 3.8 嵌入式视频模式架构未覆盖

**现状**：Phase 3 学习视频有三种模式（嵌入/授权本地化/UGC），架构 `learning_video` 模块提到了三种模式但未设计嵌入模式的技术方案。

**缺失内容**：
- 嵌入模式实现：iframe 嵌入第三方播放器（B站/抖音/YouTube）？
- 外链可用性监控（外部视频可能下架）
- 版权声明和来源标注
- 嵌入视频与平台内视频在信息流中的统一展示

**建议**：在 learning_video 模块补充三种模式的技术实现方案

## 十、结论

架构文档 v1.0 整体质量优秀，技术选型与 Phase 0 结论完全对齐，模块划分覆盖了 Phase 1-4 的全部功能需求。主要不足在于：

1. **缺少数据库设计和 API 设计**——这是从架构到实施的桥梁，需在进入详细设计前补充
2. **几个非平凡功能未设计实现方案**——乒乓大数据间接胜利、智能组队、视频转码等
3. **运维侧设计不足**——熔断降级、监控告警、成本控制、PIPL 合规

建议按 P0/P1 优先级补充后再进入详细设计阶段。P2/P3 可与详细设计同步迭代。
