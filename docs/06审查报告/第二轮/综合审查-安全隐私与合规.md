## 2. 维度一：认证与授权

### 2.1 现状概述

系统采用双层认证体系：

- **用户端**：JWT 双 Token 机制（access token 15min + refresh token 7d），微信小程序登录（`code → openid → JWT`），H5 场景使用 5min 短 token + 静默刷新
- **管理后台**：独立 `AdminUser` 表 + Redis session（30min TTL），RBAC 三角色（`super_admin` / `content_admin` / `model_admin`）
- **WebSocket**：连接时通过 URL query param 传递 JWT token 进行认证
- **会员权限**：`MembershipService.check_membership()` 返回等级和额度状态，`require_membership("member")` 依赖用于特定端点

### 2.2 发现项

#### [SEC-001] P0 — Refresh Token 未被撤销，logout 后仍可刷新获取新 Token

- **来源文档**：`01-auth/backend.md` §5 `AuthService.logout()`
- **描述**：logout 方法仅将 access token 的 `jti` 加入 Redis 黑名单（`jwt:blacklist:{jti}`，TTL = access token 剩余有效期），但 **refresh token 未被撤销**。攻击者若已获取 refresh token，在用户 logout 后仍可用其生成新的 access token，实现持续访问。
- **风险**：认证撤销不完整，session hijacking 后无法通过 logout 终止攻击
- **修复建议**：
  - logout 时同时将 `refresh_token:{jti}` 加入 Redis 黑名单，TTL = refresh token 剩余有效期
  - `refresh_token()` 方法在校验 refresh token 有效性时，增加 Redis 黑名单检查
  - 建议使用 Redis `SADD` 维护用户级 token 白名单，logout 时批量移除

#### [SEC-002] P1 — WebSocket Token 经 URL Query Param 传递

- **来源文档**：`12-notification/backend.md` §6.2 `websocket_endpoint(token: str = Query(...))`
- **描述**：WebSocket 连接时 JWT token 通过 `?token=xxx` URL 参数传递。URL 参数可能被以下途径泄露：
  - Nginx / 反向代理 access log
  - 浏览器 history / referrer header
  - CDN 边缘日志
- **风险**：Token 泄露导致 WebSocket 连接被劫持
- **修复建议**：
  - 改用 WebSocket 子协议（`Sec-WebSocket-Protocol` header）传递 token
  - 或使用 `Authorization` header（需 WebSocket 客户端支持）
  - 如必须使用 query param，需在反向代理层配置 `access_log` 过滤 token 参数

#### [SEC-003] P1 — 会员权限守卫覆盖不完整

- **来源文档**：`07-training_advice/backend.md` §6（`require_membership("member")` 仅用于 `re-evaluate` 端点）、`10-membership/backend.md`
- **描述**：架构 §11 要求会员功能（训练方案、3D 教学、进度分析等）需会员及以上等级。但切片实现中：
  - `re_evaluate_plan` 正确使用了 `require_membership("member")`
  - 但 `get_plan_adjustments`、`list_training_sessions` 等端点仅需 `get_current_user`（登录即可）
  - 前端降级策略（隐藏入口）仅为前端方案，后端缺少统一守卫
- **风险**：免费用户可通过直接调用 API 绕过前端限制，访问会员功能
- **修复建议**：在所有会员专属端点添加 `require_membership("member")` 依赖，不依赖前端隐藏入口

#### [SEC-004] P2 — JWT 算法未限制

- **来源文档**：`01-auth/backend.md` §4 `create_access_token()` / `decode_token()`
- **描述**：`decode_token()` 使用 `jwt.decode(token, key, algorithms=["HS256"])` 已限制算法为 HS256（良好实践）。但 `create_access_token()` 使用对称密钥签名，若未来引入非对称密钥需注意 `alg=none` 攻击防护。当前实现安全。
- **风险**：低（当前实现已限制算法）
- **修复建议**：保持当前实现，确保未来不引入 `alg=none` 允许

#### [SEC-005] P2 — 跨用户数据访问防护不完整

- **来源文档**：`05-match_data/backend.md`（`MatchDataService` 查询时 `user_id == user.id` 过滤）、`02-user/backend.md`（`get_export_status` 查询时 `ExportTask.user_id == user.id` 过滤）
- **描述**：大部分 Service 方法正确使用 `user_id` 过滤查询，如 `MatchDataService.get_detail()` 使用 `MatchRecord.user_id == user_id` 查询。但 `get_template_detail()`（训练模板详情）未校验模板是否为公共模板，任何登录用户均可查看（设计上模板为公共数据，可接受）。
- **风险**：低（跨用户数据隔离在核心模块已实现）
- **修复建议**：保持当前实现，在 Code Review 中持续验证新增 Service 方法包含 `user_id` 过滤

#### [SEC-006] P3 — H5 Token 与小程序 Token 安全级别一致

- **来源文档**：`01-auth/backend.md` §5 H5 5min token + 静默刷新
- **描述**：H5 场景使用 5min 短 access token + 30min refresh token，安全级别设计合理（短 TTL 降低泄露风险）。观察项：H5 场景的 refresh token 同样存在 SEC-001 的问题。
- **风险**：信息性
- **修复建议**：随 SEC-001 修复一并处理

## 3. 维度二：PIPL 合规

### 3.1 现状概述

系统在 PIPL（个人信息保护法）合规方面已实现以下基础能力：

- **数据可携带权**：`POST /users/export-data` 异步导出个人数据（Celery + ExportTask 表），每月限 1 次
- **删除权**：`DELETE /users/account` 用户注销（72h 冷静期 + `pending_deletion` 状态）
- **最小必要原则**：免费用户每日 3 次分析额度限制

### 3.2 发现项

#### [PIPL-001] P0 — 缺少用户同意记录机制（consent_log）

- **来源文档**：DB 设计 v1.4（无 consent_log 表定义）、架构 v2.4 §11（无同意记录规范）、需求 v0.4（无同意收集需求）
- **描述**：PIPL 第 14 条要求处理个人信息需取得个人同意，且需保存同意记录。系统当前：
  - 微信登录时通过 `wx.login` 获取 openid，用户未显式同意隐私政策
  - 无 `consent_log` 表或类似机制记录用户同意的时间、版本、范围
  - 首次登录时未展示隐私政策弹窗或同意流程
- **风险**：无法证明已取得用户同意，违反 PIPL 第 14 条
- **修复建议**：
  - 新建 `consent_log` 表（`id, user_id, consent_type, policy_version, consent_at, ip_address`）
  - 首次登录时强制展示隐私政策弹窗，用户点击同意后记录
  - 隐私政策更新时需重新获取同意

#### [PIPL-002] P1 — 数据导出缺少导出内容清单和审计日志

- **来源文档**：`02-user/backend.md` §5 `UserService.export_data()`
- **描述**：数据导出功能存在但存在以下不足：
  - 导出任务创建时未记录导出请求的 IP 地址和设备信息
  - 导出内容缺少清单说明（导出了哪些数据、格式、范围）
  - 导出链接 7 天有效但缺少下载次数限制
  - `export_task` 表缺少 `requested_ip` / `downloaded_at` 等审计字段
- **风险**：无法追溯数据导出行为，PIPL 第 45 条要求个人信息处理者需记录个人信息处理情况
- **修复建议**：
  - `export_task` 表新增 `requested_ip`、`user_agent`、`downloaded_at`、`download_count` 字段
  - 导出链接设置单次下载或限 3 次下载
  - 导出文件中包含数据清单说明

#### [PIPL-003] P1 — 用户注销后数据清理缺少验证机制

- **来源文档**：`02-user/backend.md` §5 `UserService.delete_account()` — 设置 `pending_deletion` 状态 + 72h 后执行永久删除（Celery 延迟任务，代码中被注释）
- **描述**：注销流程设计为：
  1. 用户提交注销 → 状态设为 `pending_deletion`，`scheduled_deletion_at = now + 72h`
  2. 72h 后 Celery 延迟任务执行永久删除
  3. 重复提交返回 409

  存在问题：
  - Celery 延迟任务代码被注释（`# permanent_delete_user.apply_async(...)`），实际未投递
  - 缺少永久删除的具体实现（哪些表删除、哪些字段匿名化）
  - 缺少删除验证机制（删除后如何验证数据确实被清除）
  - OSS 视频/标注视频等文件存储的清理未定义
- **风险**：注销请求后数据实际未被清理，违反 PIPL 第 47 条
- **修复建议**：
  - 实现 `permanent_delete_user` Celery 任务：删除用户数据表记录（match_record, analysis_report, video_task 等）、匿名化 user 表关键字段、清理 OSS 文件
  - 删除完成后写入 `deletion_confirmation` 记录（删除时间、操作人、影响表清单）
  - 在 `delete_account()` 中取消注释 Celery 任务投递

#### [PIPL-004] P2 — 视频上传缺少"最小必要"原则限制

- **来源文档**：`01-auth/backend.md`（视频上传未限制时长/大小）、需求 v0.4（未定义视频上传限制）
- **描述**：PIPL 第 6 条要求处理个人信息应遵循最小必要原则。视频分析场景中，用户上传的视频可能包含场地中其他人员的面部信息。当前缺少：
  - 视频时长 / 文件大小限制
  - 视频中非用户面部信息处理说明
  - 视频原始文件保留策略（分析完成后是否删除原始视频）
- **风险**：过度收集个人信息，违反最小必要原则
- **修复建议**：
  - 定义视频上传限制（如最大 500MB / 10 分钟）
  - 分析完成后按策略删除原始视频（如保留 7 天后清理）
  - 隐私政策中说明视频中可能包含其他人员信息

## 4. 维度三：数据留存与生命周期

### 4.1 现状概述

系统在数据生命周期管理方面已有以下设计：

- **OSS 文件生命周期**：架构 §12.10 提及 OSS 生命周期规则
- **notification_record**：切片注释提及应按月分区 + 3 个月清理（未落地）
- **标注视频降级清理**：会员到期后保留 30 天后清理（Redis 标记）
- **export_task 下载链接**：7 天有效
- **Soft Delete**：file_management 使用软删除 + 孤儿清理

### 4.2 发现项

#### [RET-001] P1 — notification_record 分区和清理策略未落地

- **来源文档**：`12-notification/backend.md` §3 Model 注释："notification_record 表应按月分区（PARTITION BY RANGE (created_at)），3 个月前的数据通过 pg_cron 自动清理"
- **描述**：分区策略仅在 Model 定义注释中说明，但：
  - Alembic 迁移仅创建普通表（`CREATE TABLE`），未创建分区表 DDL
  - pg_cron 清理任务未配置
  - 3 个月后的数据将持续堆积，影响查询性能
- **风险**：notification_record 表数据无限增长，查询性能退化
- **修复建议**：
  - Alembic 迁移中使用 `CREATE TABLE ... PARTITION BY RANGE (created_at)` 创建分区表
  - 配置 pg_cron 定时任务每月创建新分区 + 清理 3 个月前分区
  - 或使用 Celery Beat 定时任务清理超期数据

#### [RET-002] P1 — 标注视频降级清理缺少实际清理任务

- **来源文档**：`10-membership/backend.md` §5 `apply_downgrade_policy()` — 设置 Redis 标记 `downgrade:video:cleanup:{user_id}`（30 天 TTL）
- **描述**：降级策略通过 Redis TTL 标记需要清理的标注视频，但：
  - Redis TTL 过期后仅删除标记，不触发实际文件清理
  - 缺少 Celery 定时任务扫描过期标记并清理 OSS 文件
  - `downgrade:report:readonly:{user_id}` 使用 `redis.set()` 无 TTL，永久驻留 Redis
- **风险**：标注视频文件持续占用 OSS 存储空间，降级策略实际未生效
- **修复建议**：
  - 实现 Celery Beat 定时任务（每日扫描），检查 `downgrade:video:cleanup:*` 标记
  - 标记存在时删除对应 OSS 文件 + DB 记录
  - `downgrade:report:readonly` 设置合理 TTL 或在用户续费时主动删除

#### [RET-003] P2 — OSS 生命周期规则缺少具体策略

- **来源文档**：架构 v2.4 §12.10（提及 OSS 生命周期规则但未定义具体策略）
- **描述**：架构提及 OSS 生命周期规则但未说明：
  - 原始视频文件的留存期限
  - 标注视频文件的留存期限
  - 分析报告 JSONB 数据的留存期限
  - 头像等用户文件的留存期限
- **风险**：OSS 存储成本持续增长，缺少自动化生命周期管理
- **修复建议**：
  - 定义 OSS 生命周期规则：原始视频分析完成后 7 天删除、标注视频按会员状态管理、用户头像永久保留
  - 在架构文档中补充 OSS 生命周期策略表

#### [RET-004] P2 — ExportTask 记录未设置清理策略

- **来源文档**：`02-user/backend.md` §3 `ExportTask` 表
- **描述**：`export_task` 表记录所有导出任务，但未定义清理策略。下载链接 7 天过期后，任务记录将永久驻留数据库。
- **风险**：export_task 表数据持续增长
- **修复建议**：定义 Celery Beat 定时任务，定期清理 90 天前的已完成 export_task 记录

#### [RET-005] P3 — 软删除策略一致性观察

- **来源文档**：`13-infrastructure/file_management.md`（软删除 + 孤儿清理 1h）
- **描述**：file_management 使用软删除（`is_deleted` 字段）+ 孤儿清理（1 小时 TTL）。表述"1 天 vs 1 小时"在不同文档中可能引起混淆。架构 §12.10 使用"1 天"，切片使用"1 小时"。
- **风险**：信息性（不影响安全性）
- **修复建议**：统一文档表述，架构与切片保持一致

## 5. 维度四：限流与防滥用

### 5.1 现状概述

系统使用 `slowapi`（`@limiter.limit()`）实现 API 限流：

- **全局默认**：100/minute（所有 REST API 端点）
- **打卡端点**：`1/day`（按用户限流，`key_func=lambda r: r.state.user`）
- **AI 分析创建**：架构要求 `10/hour`（部分切片实现）
- **WebSocket**：不需要 slowapi 限流（连接级限流由 WS 层处理）

### 5.2 发现项

#### [RL-001] P1 — 微信支付回调端点被错误限流

- **来源文档**：`11-payment/backend.md` §6 `@limiter.limit("100/minute") @router.post("/notify")`
- **描述**：微信支付回调端点 `POST /payment/notify` 添加了 `@limiter.limit("100/minute")` 限流装饰器。微信支付服务器在支付成功后会重试回调（最多 8 次，间隔递增），若回调被限流拒绝（返回 429），微信将重试，但若持续被限流则回调可能永久失败，导致用户支付成功但订单状态不更新。
- **风险**：支付回调被限流 → 订单状态不更新 → 用户已付款但无法获得服务
- **修复建议**：
  - 移除 `/payment/notify` 端点的 `@limiter.limit()` 装饰器
  - 或改为基于 IP 的高频限流（如 `1000/minute`，仅防止恶意刷接口）
  - 回调端点已有 RSA 签名验证，可替代限流的防滥用功能

#### [RL-002] P2 — AI 分析创建限流未统一实现

- **来源文档**：架构 v2.4 §11 要求"AI 分析创建 10/hour"，各切片反幻觉约束中提及"AI 分析创建 10/hour"
- **描述**：架构要求 AI 分析创建端点限流为 `10/hour`，但：
  - `03-video_analysis/backend.md` 中 `create_task` 端点的限流装饰器未在审查范围内确认
  - 各切片反幻觉约束中提及"ALL API 端点已添加 `@limiter.limit()` 限流装饰器，全局默认 100/minute，AI 分析创建 10/hour"，但实际代码中未看到 `10/hour` 的实现
- **风险**：免费用户可能高频创建分析任务，消耗 GPU 资源
- **修复建议**：
  - 在 `POST /video-analysis/tasks` 端点显式添加 `@limiter.limit("10/hour")` 装饰器
  - 与 `MembershipService.consume_analysis_quota()` 配合，双重保障

#### [RL-003] P2 — 训练提醒频率控制存在竞态条件

- **来源文档**：`12-notification/backend.md` §5 `send_training_reminder()` — 检查 `_check_reminder_frequency()` 后 `INCR` 计数
- **描述**：训练提醒频率控制使用 Redis 计数器（`notif:reminder:count:{user_id}:week`），流程为：
  1. 检查 `current < 2`
  2. 发送通知
  3. `INCR` 计数

  步骤 1 和 3 非原子操作，并发场景下可能同时通过检查，导致超过每周 2 次限制。
- **风险**：低（训练提醒并发场景极少），但违反频率控制约束
- **修复建议**：先 `INCR` 再检查值，若 > 2 则 `DECR` 回退并跳过发送

## 6. 维度五：输入校验与净化

### 6.1 现状概述

系统采用 Pydantic Schema 层 + Service 层双重校验：

- **Schema 层**：Pydantic `field_validator` / `model_validator` 校验字段类型、枚举值、范围
- **Service 层**：业务规则校验（如比分合法性、赛制规则）
- **参数约束**：`min_length`、`max_length`、`ge`、`le`、`Literal` 等约束

### 6.2 发现项

#### [INP-001] P1 — 用户输入字段缺少 XSS 净化

- **来源文档**：`02-user/backend.md`（`nickname` String(64) 无 HTML 过滤）、`05-match_data/backend.md`（`opponent_name` String(64) 无过滤）
- **描述**：以下用户输入字段直接存入数据库，未经过 HTML/XSS 净化：
  - `User.nickname` — String(64)
  - `MatchRecord.opponent_name` — String(64)
  - `MatchRecord.notes`（如果存在）
  - `AccountDeletionRequest.reason` — max_length=500
  - `RefundRequest.reason` — max_length=500

  若前端渲染这些字段时未做 HTML 转义，可能存在存储型 XSS 风险。
- **风险**：存储型 XSS（若前端未转义渲染）
- **修复建议**：
  - 在 Schema 层添加 `field_validator` 对文本字段进行 HTML 标签过滤（如使用 `bleach.clean()`）
  - 或在 Service 层写入数据库前统一净化
  - 前端渲染时确保使用 `v-text` / `{{ }}` 而非 `v-html`

#### [INP-002] P2 — equipment_config JSON 字段缺少深度校验

- **来源文档**：`02-user/backend.md` §4 `ProfileUpdateRequest.equipment_config: Optional[dict[str, Any]]`
- **描述**：`equipment_config` 为 `dict[str, Any]` 类型，Pydantic 仅校验顶层为 dict，不校验嵌套结构和值。恶意用户可提交超大 JSON 或深层嵌套数据。
- **风险**：DoS（大 JSON 解析消耗资源）或数据污染
- **修复建议**：
  - 定义 `EquipmentConfig` Pydantic 模型，限制 `blade`、`rubber_fh`、`rubber_bh`、`shoes` 等字段
  - 设置 `max_length` / `max_items` 约束

#### [INP-003] P2 — 比分校验 Service 层与 Schema 层逻辑重复

- **来源文档**：`05-match_data/backend.md` §4 `MatchRecordCreateRequest.validate_score()` + §5 `MatchDataService._validate_score_by_format()`
- **描述**：比分合法性校验在 Schema 层（`model_validator` 检查比分不相同 + 日期不未来）和 Service 层（`_validate_score_by_format` 检查赛制规则）双重实现。两层校验覆盖面不同但存在逻辑重叠（如"比分不相同"在两层都检查）。
- **风险**：低（逻辑重复不影响安全性，但增加维护成本）
- **修复建议**：明确分工：Schema 层校验通用规则（类型、范围、非空），Service 层校验业务规则（赛制规则）

## 7. 维度六：密钥管理

### 7.1 现状概述

系统涉及以下密钥和敏感配置：

| 密钥 | 来源 | 存储方式 |
|------|------|----------|
| `JWT_SECRET_KEY` | 架构 §14 环境变量 | `settings.JWT_SECRET_KEY` |
| `JWT_REFRESH_SECRET_KEY` | 架构 §14 环境变量 | `settings.JWT_REFRESH_SECRET_KEY` |
| `WECHAT_API_V3_KEY` | 架构 §14 环境变量 | `settings.WECHAT_API_V3_KEY` |
| `WECHAT_PRIVATE_KEY` | 架构 §14 环境变量 | `settings.WECHAT_PRIVATE_KEY` |
| `REDIS_PASSWORD` | 架构 §14 环境变量 | `settings.REDIS_PASSWORD`（可选） |
| `DATABASE_URL` | 架构 §14 环境变量 | `settings.DATABASE_URL` |

### 7.2 发现项

#### [KEY-001] P0 — JWT_SECRET_KEY 存在硬编码默认值

- **来源文档**：架构 v2.4 §14 环境变量配置
- **描述**：架构 §14 中 `JWT_SECRET_KEY` 存在默认值（如 `"your-secret-key-here"` 或类似占位符）。若生产环境部署时未覆盖此环境变量：
  - JWT 签名密钥为公开已知的默认值
  - 攻击者可使用相同密钥伪造任意用户的 JWT token
  - 完全绕过认证系统
- **风险**：认证系统被完全绕过，任意用户冒充
- **修复建议**：
  - 移除代码中的默认值，启动时若 `JWT_SECRET_KEY` 未设置则 `raise` 拒绝启动
  - 或使用 `pydantic-settings` 的 `Field(..., env="JWT_SECRET_KEY")` 强制必填
  - 生产环境使用 32+ 字符随机字符串，定期轮换

#### [KEY-002] P1 — 微信支付私钥缺少轮换策略

- **来源文档**：`11-payment/backend.md` §5 `_rsa_sign()` — `settings.WECHAT_PRIVATE_KEY.encode()`
- **描述**：微信支付 RSA 私钥从 `settings.WECHAT_PRIVATE_KEY` 读取（环境变量），但：
  - 未定义密钥轮换流程和周期
  - 私钥以 PEM 字符串存储在环境变量中，若环境变量泄露则密钥暴露
  - 微信支付平台证书（`_get_wechat_platform_cert`）从 Redis 获取，但缺少自动更新机制
- **风险**：私钥泄露后无法快速轮换
- **修复建议**：
  - 定义密钥轮换流程文档（如每 6 个月轮换一次）
  - 私钥存储使用 KMS（如阿里云 KMS）而非环境变量
  - 平台证书自动更新：定期调用微信 API 获取最新平台证书并缓存到 Redis

#### [KEY-003] P1 — Redis AUTH 为可选项

- **来源文档**：架构 v2.4 §14 — `REDIS_PASSWORD` 为可选配置
- **描述**：Redis 密码在架构中为可选项。若生产环境未设置 Redis 密码：
  - 任何能访问 Redis 端口的机器可读写 Redis 数据
  - Redis 中存储了 JWT 黑名单、用户额度计数器、连续打卡天数、WS 在线状态等敏感数据
  - 攻击者可修改额度计数器获取无限免费分析次数
- **风险**：Redis 数据被未授权访问和篡改
- **修复建议**：
  - 生产环境强制设置 Redis 密码
  - Redis 配置 `requirepass` 或使用 ACL
  - 架构文档中将 `REDIS_PASSWORD` 标注为"生产环境必填"

#### [KEY-004] P2 — 密钥轮换策略整体缺失

- **来源文档**：架构 v2.4 §11 安全规范（无密钥轮换章节）
- **描述**：系统缺少整体密钥轮换策略：
  - JWT 密钥无轮换计划
  - 微信支付密钥无轮换计划
  - 数据库密码无轮换计划
  - 无密钥泄露应急响应流程
- **风险**：密钥泄露后无法快速响应
- **修复建议**：
  - 制定密钥轮换策略文档
  - JWT 密钥支持双密钥过渡期（old + new 同时验证，逐步切换）
  - 定义密钥泄露应急响应流程

## 8. 维度七：审计日志

### 8.1 现状概述

系统审计日志能力如下：

- **管理后台**：`admin` 基础设施切片实现了完善的 `audit_log` 全操作记录（RBAC 操作、内容管理操作、用户管理操作等）
- **用户端**：`02-user/backend.md` 中用户敏感操作（注销、数据导出）**未写入 audit_log**
- **支付模块**：`11-payment/backend.md` 中订单创建、退款、回调处理**未写入 audit_log**

### 8.2 发现项

#### [AUD-001] P0 — 支付操作缺少审计日志

- **来源文档**：`11-payment/backend.md` §5 `PaymentService`（create_order、handle_notify、refund 均无 audit_log 写入）
- **描述**：支付模块的以下敏感操作未写入审计日志：
  - `create_order()` — 订单创建（金额、产品类型、用户）
  - `handle_notify()` — 微信回调处理（订单状态变更、支付记录创建）
  - `refund()` — 退款操作（退款金额、操作人、退款原因）
  - `_create_or_renew_subscription()` — 会员订阅创建/续期

  对比：`admin` 模块对所有管理操作均写入 `audit_log`（`admin_id, action, target_type, target_id, detail, ip_address`）。
- **风险**：支付操作无法追溯，发生纠纷时缺少证据链。PIPL 第 55 条要求个人信息处理者需采取必要措施保障个人信息安全，审计日志是重要措施。
- **修复建议**：
  - 在 `PaymentService` 的 `create_order`、`handle_notify`、`refund` 方法中写入 `audit_log`
  - 审计日志字段：`user_id, action, target_type="order", target_id=order.id, detail={amount, product_type, status}, ip_address`
  - 退款操作记录 `operator_id`（管理员 ID）

#### [AUD-002] P1 — 用户敏感操作缺少审计日志

- **来源文档**：`02-user/backend.md` §5 `UserService.delete_account()` / `export_data()`
- **描述**：以下用户敏感操作未写入审计日志：
  - `delete_account()` — 用户注销申请（影响个人信息留存）
  - `export_data()` — 个人数据导出（PIPL 数据可携带权行使记录）
  - `update_rating()` — 积分变更（涉及用户数据完整性）

  对比：admin 模块的内容管理操作有完整审计。
- **风险**：PIPL 第 56 条要求个人信息处理者定期对其个人信息处理活动进行合规审计，缺少操作日志无法合规审计。
- **修复建议**：
  - 在 `delete_account` 中写入审计日志：`user_id, action="account_deletion_request", detail={reason, scheduled_at}`
  - 在 `export_data` 中写入审计日志：`user_id, action="data_export", detail={task_id, requested_at}`
  - 实际删除执行时写入：`action="account_deleted", detail={deleted_tables, confirmed_at}`

#### [AUD-003] P1 — 审计日志缺少 IP 地址和 User-Agent

- **来源文档**：`13-infrastructure/admin.md` — `audit_log` 表定义包含 `ip_address` 字段，但各 Service 方法中写入审计日志时未传入 `ip_address`
- **描述**：admin 模块的 `audit_log` 表设计包含 `ip_address` 字段（良好），但：
  - 需确认各 Service 方法写入 audit_log 时是否实际填充了 `ip_address`
  - 用户端操作（若未来添加审计日志）同样需要 IP 地址和 User-Agent
  - FastAPI 中获取 IP 地址需通过 `request.client.host`，需在路由层传入 Service
- **风险**：审计日志缺少关键溯源信息
- **修复建议**：
  - 在路由层通过 `request: Request` 获取 `ip_address` 和 `user_agent`
  - 传递给 Service 方法并写入 audit_log

#### [AUD-004] P2 — 审计日志保留策略未定义

- **来源文档**：DB 设计 v1.4 `audit_log` 表（无保留策略字段）、架构 v2.4（无审计日志保留策略）
- **描述**：`audit_log` 表会持续增长，但未定义数据保留和归档策略。PIPL 要求个人信息处理记录至少保存 3 年。
- **风险**：审计日志无限增长影响查询性能，或未达法定保留期限被清理
- **修复建议**：
  - 定义审计日志保留策略：至少 3 年（PIPL 要求），建议 5 年
  - 1 年内的日志在 PostgreSQL 主表，超过 1 年的归档到冷存储

## 9. 维度八：网络安全

### 9.1 现状概述

系统网络安全相关设计：

- **微信支付回调验签**：APIv3 RSA-SHA256 验签 + AES-256-GCM 解密
- **HTTPS**：架构提及使用 HTTPS（通过 Nginx 反向代理）
- **CORS**：FastAPI 中间件配置（具体策略未在审查文档中定义）

### 9.2 发现项

#### [NET-001] P1 — CORS 配置策略未明确

- **来源文档**：架构 v2.4 §11 安全规范（无 CORS 配置说明）、各切片路由文件（无 CORS 中间件配置）
- **描述**：系统未在任何文档中明确 CORS（跨域资源共享）配置策略：
  - `allow_origins` 是否限制为小程序域名？
  - `allow_methods` 是否限制为必要方法？
  - `allow_headers` 是否包含 `Authorization`？
  - `allow_credentials` 是否为 True？
- **风险**：CORS 配置过于宽松可能导致跨域攻击
- **修复建议**：
  - 在架构文档中明确 CORS 配置策略
  - 生产环境 `allow_origins` 限制为已知域名列表
  - 禁止使用 `allow_origins=["*"]` + `allow_credentials=True`

#### [NET-002] P2 — 安全 HTTP 头未配置

- **来源文档**：架构 v2.4 §11（无安全 HTTP 头说明）、各切片路由（无安全头中间件）
- **描述**：系统未配置以下安全 HTTP 头：
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY`
  - `Strict-Transport-Security` (HSTS)
  - `Content-Security-Policy` (CSP)
  - `X-XSS-Protection`
- **风险**：缺少安全头增加 XSS、点击劫持等攻击面
- **修复建议**：
  - 在 FastAPI 中添加安全头中间件（或使用 `starlette-securehead`）
  - Nginx 反向代理层配置安全头

#### [NET-003] P2 — 内部服务间通信缺少认证

- **来源文档**：`13-infrastructure/ai_pipeline.md` §5.2 — AI 推理服务调用 `httpx.post(f"{INFERENCE_BASE_URL}/infer/...")` 无认证
- **描述**：AI 流水线调用 GPU 推理服务（`http://gpu-service:8501`）时未携带认证信息：
  - 无 API Key 或 JWT
  - 无 mTLS 双向认证
  - 依赖网络隔离（内网不可公开访问）
- **风险**：若内网被突破，推理服务可被未授权调用
- **修复建议**：
  - 推理服务添加 API Key 认证
  - 或使用 mTLS（服务间双向证书认证）
  - 限制推理服务仅接受内网 IP 请求

#### [NET-004] P3 — Nginx 反向代理配置未审查

- **来源文档**：架构 v2.4 §12 部署架构（提及 Nginx 但无具体配置）
- **描述**：Nginx 反向代理的具体配置（rate limiting、IP 白名单、SSL 配置、日志格式等）不在审查文档范围内。观察项：需在部署时确认 Nginx 安全配置。
- **风险**：信息性（部署阶段需确认）
- **修复建议**：制定 Nginx 安全配置基线文档，部署时验证

## 11. Optimization Opportunities（优化建议）

### 11.1 安全架构优化

1. **统一权限守卫层**（P1）
   - 创建 `app/core/deps.py` 中的 `require_tier(tier: str)` 通用依赖
   - 所有会员专属端点统一使用 `Depends(require_tier("member"))`
   - 避免依赖前端隐藏入口的降级策略

2. **Token 撤销机制优化**（P0）
   - 使用 Redis `SET` 维护用户级 active token 白名单
   - logout 时删除用户所有 active tokens
   - 支持管理员强制下线（admin 模块调用）
