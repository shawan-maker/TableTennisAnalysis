### 2.2 发现

#### BL-1 [P0] DB 设计 pro/coach 年价与需求及切片不一致

| 来源 | pro 年价 | coach 年价 |
|------|---------|-----------|
| 需求 v0.4 §会员定价 | ¥358 (35800 分) | ¥899 (89900 分) |
| DB 设计 v1.4 §8.1 | **38800 分 (¥388)** ❌ | **99000 分 (¥990)** ❌ |
| 切片 TIER_SEEDS | 35800 分 ✅ | 89900 分 ✅ |
| 前端 TIER_PRICING | ¥358 ✅ | ¥899 ✅ |

**影响**：DB 设计 §8.1 的种子数据 `price_yearly` 值与需求定义、切片实现、前端展示均不一致。若按 DB 种子数据初始化生产环境，pro 用户年付将被多收 ¥30、coach 用户年付将被多收 ¥91。

**根因**：DB 设计文档在 v1.4 更新时可能基于旧版定价（v0.1 需求中专业版 ¥799/年），未同步 v0.4 的最终定价。

**修复建议**：将 DB 设计 §8.1 `membership_tier_config` 种子数据中 pro 的 `price_yearly` 从 38800 改为 35800，coach 的从 99000 改为 89900。

#### BL-2 [P2] API §11.1 GET /membership/tiers 响应示例缺少 pro/coach 等级

| 来源 | 返回的 tiers |
|------|------------|
| API v1.3 §11.1 | 仅 `free` + `member` 两条 |
| 切片 TIER_SEEDS | `free` + `member` + `pro` + `coach` 四条 |
| 前端 TIER_ORDER | `['free', 'member', 'pro', 'coach']` 四条 |

**影响**：API 文档示例不完整，前端开发者参照 API 文档时可能遗漏 pro/coach 等级的渲染。

**修复建议**：补充 API §11.1 响应示例中 pro 和 coach 的完整 tier 对象。

#### BL-3 [P3] 会员权益列表措辞在不同文档间存在细微差异

| 等级 | 需求 v0.4 | DB 设计 §8.1 | 切片 TIER_SEEDS |

| pro | +高级分析 + 对手建模 + 月度报告 | ["高级分析","对手分析","月度报告","PDF导出"] | ["无限分析","高级分析","对手建模","月度报告","训练方案"] |

**影响**：低风险。需求文档为高层次描述，DB/切片在实现时自然增加了细节项（如 3D 教学、训练单、PDF 导出）。但"对手建模" vs "对手分析"的措辞差异可能导致前端展示文案不一致。

**修复建议**：统一权益项的命名，建议以切片 TIER_SEEDS 为基准，需求文档补充注明"权益列表以 DB 种子数据为准"。

### 3.2 发现

#### BL-4 [P2] 游戏化积分为同步调用而非事件驱动

| 来源 | 描述 |
|------|------|
| 架构 v2.4 §12.7 | 级联触发通过 Celery 异步任务（`celery_app.send_task`） |
| 切片 09 | `GamificationService.add_points()` 被直接 import 并同步调用 |
| 切片 03/04/05/07 | video_analysis、scoring、match_data、training_advice 均 `from app.services.gamification_service import GamificationService` |

**影响**：4 个模块同步调用 gamification 的 DB 操作。若 gamification 服务故障（如 `user_points` 表锁超时），调用方操作也会失败——用户完成了比赛/分析/训练但积分未增加，体验受损。

**根因**：架构设计的级联触发（`_trigger_cascade`）是异步的，但各模块在自身业务逻辑中直接调用 gamification 加分（非通过级联），这部分是同步的。

**修复建议**：
- 短期：在调用方将 gamification 加分包装在 try-except 中，失败时记录日志但不阻塞业务操作。
- 中期：改用 Celery 异步任务触发加分，或引入领域事件机制。

#### BL-5 [P3] 徽章条件评估的 metric 列表未在任何文档中定义

| 来源 | 定义 |
|------|------|
| 架构 v2.4 §9.1 | `badge_definition.condition` JSONB: `{metric, operator, threshold}` |
| DB 设计 v1.4 §3.1.4 | `condition TEXT`（存储 JSON 字符串） |
| 切片 09 | `_check_badges()` 遍历 badge_definition，解析 condition JSONB |
| API v1.3 §10.4 | 返回 earned + locked 列表（locked 含 progress/target） |

**问题**：可用的 metric 名称（如 `total_analyses`, `win_streak`, `training_sessions_completed`）、支持的 operator 枚举（`==, >=, <=, >, <`）未在任何文档中定义。切片实现为通用 JSONB 解析，但 metric 名称的权威列表缺失，可能导致后续运营新增徽章时使用未实现的 metric。

**修复建议**：在架构 §9 或模块详细设计中补充徽章条件评估规范，定义可用 metric 列表、支持的 operator 枚举、示例徽章定义。

#### BL-7 [P1] finish_match 向 JSONB 字段写入 JSON 字符串

| 来源 | 代码 | 问题 |
|------|------|------|
| 切片 04 `finish_match` L920 | `stats_data=json.dumps(stats, ensure_ascii=False)` | 向 JSONB 字段写入 `str` 而非 `dict` |
| 切片 04 `get_statistics` L988 | `json.loads(stat.stats_data) if isinstance(stat.stats_data, str) else stat.stats_data` | 读取时做 `isinstance` 判断兼容 |
| 切片 04 Celery Beat L1251 | `stats_data=json.dumps({"note": "超时自动结束"}, ensure_ascii=False)` | 同样写入 JSON 字符串 |

**影响**：`MatchStatistic.stats_data` 在 DB 设计 v1.4 §2 中定义为 `JSONB` 类型。SQLAlchemy 的 `JSONB` 类型期望接收 Python `dict`/`list`，由驱动层自动序列化。切片代码传入 `json.dumps()` 返回的字符串，可能导致：
1. 数据库实际存储的是被 JSONB 双重编码的字符串（`"\"{...}\""`），而非原生 JSONB 对象。
2. 直接 SQL 查询 `stats_data->>'score_distribution'` 无法正常工作。
3. `get_statistics` 中的 `isinstance(stat.stats_data, str)` 兼容代码暗示开发者已意识到此问题，但未从根源修复。

**修复建议**：将 `finish_match` 和 Celery Beat 中的 `stats_data=json.dumps(...)` 改为 `stats_data=stats`（直接传 dict），移除 `get_statistics` 中的 `isinstance` 兼容逻辑。

### 5.2 发现

#### BL-8 [P1] AI 流水线步骤名称与架构定义严重不一致

| Step # | 架构 v2.4 §6.1 | 切片 PIPELINE_STEPS | 差异 |
|--------|---------------|---------------------|------|
| 1 | 视频预处理 (FFmpeg 转码/抽帧) | 视频上传完成 | 架构为处理步骤，切片为事件标记 |
| 2 | 球台检测 (YOLO-pose 四角定位) | 视频转码 | **切片缺少球台检测步骤** |
| 3 | 球体检测 (TTNet/TrackNetV5) | 球体检测 | ✅ |
| 4 | 球体追踪 (卡尔曼滤波+抛物线) | 球速估算 | 架构为追踪，切片为球速 |
| 5 | 落点估算 (单应性矩阵映射) | 球体追踪 | 顺序交换 |
| 6 | 姿态估计 (MediaPipe 2D) | 动作识别 | **切片缺少姿态估计步骤** |
| 7 | 动作识别 (Temporal CNN) | 落点分析 | 顺序交换 |
| 8 | 回合分割 (弹跳事件检测) | 回合分割 | ✅ |
| 9 | 报告生成 (规则引擎+LLM) | 统计分析 | 名称不同 |
| 10 | 标注视频生成 (FFmpeg 叠加) | 报告生成 | **切片缺少标注视频生成步骤** |

**影响**：
1. **球台检测缺失**：架构定义 Step 2 为球台检测（YOLO-pose 四角定位），是后续落点估算（单应性矩阵映射）的前置条件。切片 PIPELINE_STEPS 中无此步骤，可能导致落点分析缺少球台坐标系基准。
2. **姿态估计缺失**：架构定义 Step 6 为姿态估计（MediaPipe 2D），是动作识别（Temporal CNN）的输入。切片跳过此步骤直接做动作识别，可能导致动作识别精度下降。
3. **标注视频生成缺失**：架构定义 Step 10 为标注视频生成（FFmpeg 叠加轨迹/标注），切片无此步骤，用户无法获得可视化标注视频。
4. **前端同步问题**：前端切片 `PIPELINE_STEPS` 与后端切片一致，因此前端展示的进度步骤也与架构定义不符。

**根因**：切片设计时可能为简化冒烟测试，将 PIPELINE_STEPS 定义为面向用户展示的进度步骤（而非技术实现步骤），但未与架构文档对齐命名和内容。

**修复建议**：
- 将切片 `PIPELINE_STEPS` 与架构 §6.1 的步骤名称对齐。
- 如果切片定义为"用户可见进度"而非"技术实现步骤"，应在切片注释中明确说明映射关系。

### 7.2 发现

#### BL-12 [P1] 退款规则缺少 24h/7 天时间窗口自动执行

| 来源 | 24h 内 | 24h-7 天 | 超过 7 天 |
|------|--------|---------|---------|
| 架构 v2.4 §12.13 | 全额退款，标记 `reversed` | 人工审核，退 50% | 不支持退款 |
| 切片 11-payment | **无时间窗口判断** — 管理员可对任意已支付订单退款任意金额 | 同 | 同 |

**影响**：架构 §12.13 为创作者内容购买定义了基于时间窗口的退款规则（24h 全额、7 天 50%、超 7 天不可退），但切片的退款实现完全依赖管理员人工判断，没有时间窗口的自动校验。这意味着：
1. 管理员可能在超过 7 天后仍执行退款，违反架构规则。
2. 24h-7 天的退款金额未自动限制为 50%。
3. 架构定义的 `reversed` 标记在切片 `RefundRecord` 中无对应字段。

**说明**：架构 §12.13 明确标注为"Phase 3 创作者收益"流程，当前 Phase 1 的支付切片仅处理会员订阅退款。但会员订阅退款是否也应有时间窗口规则？需求/架构中未明确会员订阅的退款时间窗口。

**修复建议**：
1. 在切片 `refund` 方法中增加创建时间校验：超过 7 天的订单拒绝退款（返回 400）。
2. 明确会员订阅退款是否适用 24h/7 天规则，若适用则补充实现。
3. 在 `RefundRecord` 中增加 `reversal_type` 字段以支持 `reversed` 标记。

#### BL-13 [P2] 退款后会员权益撤销逻辑未在切片中实现

| 来源 | 描述 | 实现状态 |
|------|------|---------|
| 架构 v2.4 约束 #32 | 权益到期后用户数据只读降级，不删除 | membership 切片 `apply_downgrade_policy` ✅ |
| API v1.3 §12.4 | 退款回调→撤销会员权益（如适用） | 切片 11 仅更新 `order.status="refunded"`，**未调用 membership 模块撤销权益** ⚠️ |

**影响**：用户退款后，订单状态更新为 `refunded`，但会员订阅未被撤销——用户仍可享受会员权益直到自然到期。

**修复建议**：在切片 11 `refund` 方法成功后，增加对 membership 模块的调用：如果退款的是会员订阅订单，则调用 `MembershipService.revoke_subscription(subscription_id)` 撤销权益并触发降级策略。

## 12. 未考虑的边缘场景

### 12.1 会员等级

| 场景 | 当前状态 | 风险 |
|------|---------|------|
| 会员到期后有进行中的比赛 | 降级策略未提及比赛状态处理 | 进行中的比赛可能被中断 |
| 会员到期后有进行中的 AI 分析任务 | 降级策略未提及分析任务处理 | 已提交的分析任务可能无法查看结果 |
| 用户在免费额度即将用尽时并发提交多个分析请求 | Redis INCR+DECR 回退机制存在竞态条件 | 可能超额使用 1-2 次 |
| pro/coach 等级用户降级为 free 时，已有的高级分析报告是否保留 | 架构约束 #32 说"只读降级不删除"，但未明确高级分析报告的只读范围 | P2 风险 |

### 12.2 支付与退款

| 场景 | 当前状态 | 风险 |
|------|---------|------|
| 微信支付回调延迟到达（超过订单超时时间） | 切片未处理延迟回调 | 用户支付成功但订单已取消 |
| 退款时微信退款 API 超时但实际退款成功 | 切片 `_call_wechat_refund` 超时抛异常，退款记录未创建 | 用户已收到退款但系统无记录 |
| 同一订单多次退款 | 切片校验 `order.status=="paid"`，退款后状态变 `refunded`，无法二次退款 | 符合预期（全额退款），但部分退款场景不支持 |
| 微信支付回调验签失败 | 切片返回 400，不处理 | 正确行为，但缺少告警机制 |

### 12.3 比赛规则

| 场景 | 当前状态 | 风险 |
|------|---------|------|
| 多设备同时 finish 同一比赛 | 切片 `finish_match` 校验 `status=="in_progress"`，第二台设备会收到 400 | 正确行为 |
| abandoned 比赛在 24h 边界时刻 resume | 切片使用 `datetime.now(timezone.utc) - match.abandoned_at` 精确到秒 | 边界竞态（毫秒级）可接受 |
| Celery Beat 清理任务和用户 resume 同时执行 | 存在竞态：Beat 转为 finished 的同时用户尝试 resume | P3 风险，概率极低 |

### 12.4 视频分析流水线

| 场景 | 当前状态 | 风险 |
|------|---------|------|
| AI 分析中途某步骤失败 | 切片未定义部分失败的回滚/重试策略 | 已完成步骤的结果可能丢失 |
| 用户在分析进行中注销账号 | 无处理逻辑 | 分析任务可能继续执行但结果无处存储 |
| 前端 WebSocket 断连后流水线进度丢失 | 架构定义了重连后全量同步，但切片未实现 `sync_analysis` | 用户可能看不到分析进度 |

### 12.5 训练建议

| 场景 | 当前状态 | 风险 |
|------|---------|------|
| 用户首次分析（无历史数据）时生成训练建议 | 架构 §12.7 趋势计算需要历史快照，首次无历史 | 首次分析可能无法生成增强训练建议（降级为基础建议） |
| 规则引擎匹配不到任何问题 | 架构未定义 fallback 策略 | 用户可能收不到训练建议 |
| 级联触发异步任务失败 | `celery_app.send_task` 失败时无重试/告警 | 用户分析完成后无训练建议，且无感知 |

### 12.6 数据保留

| 场景 | 当前状态 | 风险 |
|------|---------|------|
| 用户注销后 72h 内再次登录 | 架构未定义此场景处理 | 可能需要"冷静期撤销"机制 |
| OSS Lifecycle 规则与 DB 记录不同步 | OSS 删除文件但 DB 仍有记录 | 查询时返回 404 但 DB 有记录 |
| 降级用户 30 天后标注视频清理时 OSS 文件已不存在 | 切片注释说"忽略 OSS 404" | 清理任务不报错但记录残留 |
