## 1. 项目概述

### 1.1 系统定位

- **产品名称**：乒乓智能分析平台 / PingPongAI
- **一句话定位**：面向中国乒乓球爱好者的 AI 驱动训练分析平台，覆盖视频智能分析、3D 数字人物教学、数据看板、赛事社区全流程
- **目标用户规模**：Phase 1 验证 1000+ 注册用户，中长期 10 万+ 活跃用户
- **核心壁垒**：数据飞轮（用户上传视频 → AI 分析 → 用户反馈 → 标注数据 → 模型 fine-tune → 精度提升 → 更多用户上传）

### 1.2 核心用户角色

| 角色 | 权限范围 | 典型操作 |
|------|---------|---------|

| 专业用户 | 专业权益 | 高级分析、对手建模、月度报告 |
| 教练用户 | 教练权益 | 学员管理、批量分析、教练工具、线上指导服务 |
| 创作者 | 内容管理 | 上传教学视频、定价、收益管理 |
| 管理员 | 全局管理 | 内容审核、用户管理、系统配置、模型管理 |

### 2.2 跨平台方案选型决策

> **决策结论：选择 Taro 4（React 体系），排除 uni-app（Vue 体系）。**

| 维度 | Taro 4 (React) | uni-app (Vue) | 决策依据 |
|------|---------------|--------------|---------|
| 3D 生态对齐 | ✅ React Three Fiber 原生支持 | ❌ Vue 3D 生态弱（TresJS 不成熟） | Phase 0 确定 R3F，Taro 与之天然对齐 |
| 小程序 3D 适配 | ✅ threejs-miniprogram 适配版 | ✅ 同样支持 | 两者均可，但 Taro 更好封装 |
| App 渲染层 | React Native + WebView（3D 用 H5） | nvue/Weex + WebView | RN 生态更大，WebView 方案两者一致 |
| 一码多端 | 微信小程序 + H5 + RN App | 微信小程序 + H5 + App | 均满足，Taro 编译产物更标准 |
| TypeScript 支持 | ✅ 原生支持 | ✅ 原生支持 | 两者均满足 |
| 维护活跃度 | 京东团队，持续更新 | DCloud，持续更新 | 两者均活跃 |
| 社区规模 | GitHub 35k+ star | GitHub 40k+ star | 两者均成熟 |

**3D 跨端策略**：

| 平台 | 3D 渲染方案 | 说明 |
|------|-----------|------|
| 微信小程序 | threejs-miniprogram（基于 Three.js 0.108 定制） | 小程序 WebGL 适配，体积减少 40% |
| App（iOS/Android） | React Native WebView 嵌入 H5 + React Three Fiber | WebView 渲染 WebGL，性能可达 30-60fps |
| H5 | React Three Fiber + @react-three/drei | 完整 R3F 生态，最佳开发体验 |

> 3D 核心场景逻辑（模型加载、动画播放、OrbitControls）封装为平台无关的 Three.js 模块，各端通过薄适配层调用，减少代码重复。

### 2.7 关键选型补充说明

#### 放弃微信云开发的理由

需求 v0.4 提到"微信云开发（小程序端）+ 独立云服务（App端）"，架构最终选择**统一 FastAPI 后端**，放弃微信云开发。

| 维度 | 微信云开发 + 独立云服务（双后端） | 统一 FastAPI 后端（本方案） |
|------|-------------------------------|------------------------|
| 后端维护数 | 2 套（云函数 + FastAPI） | 1 套（FastAPI） |
| 业务逻辑同步 | 需在两套后端间同步，易出错 | 统一一份，无同步问题 |
| AI 集成 | 云函数不支持 GPU 推理，仍需独立 AI 服务 | 统一调用 AI 推理服务 |
| 数据一致性 | 云开发数据库与 PostgreSQL 数据同步复杂 | 统一 PostgreSQL |
| 个人开发效率 | 双后端维护成本翻倍 | 单后端，效率最大化 |
| 小程序适配 | 云开发天然支持 | FastAPI 通过 HTTP API 对接小程序，无障碍 |

> **结论**：个人开发场景下，维护双后端是不可承受的成本。FastAPI 统一后端通过 HTTP API 服务小程序和 App，微信云开发不提供不可替代的能力。

#### 排除 MongoDB 的理由

需求 v0.4 提到"MongoDB / PostgreSQL"，架构最终选择 **PostgreSQL**。

| 维度 | MongoDB | PostgreSQL（本方案） |
|------|---------|-------------------|
| JSON 存储 | 原生文档数据库 | JSONB 字段，功能等价且支持索引 |
| ACID 事务 | 4.0+ 支持多文档事务，但复杂 | 成熟 ACID，支付/记分场景必须 |
| 地理查询 | 2dsphere 索引，功能基本 | PostGIS，功能更强、生态更成熟 |
| 关系查询 | 不擅长 JOIN | 原生关系查询，赛事/订单/积分场景必需 |
| ORM 支持 | Motor/Odmantic（异步但不成熟） | SQLAlchemy 2.0 async（最成熟） |
| 团队熟悉度 | 一般 | 更通用，文档/社区更丰富 |

> **结论**：PostgreSQL 的 JSONB 已满足 JSON 存储需求，同时提供 ACID 事务（支付/记分）、PostGIS（LBS 查询）、成熟关系查询（赛事/订单/积分），无需引入 MongoDB 增加运维复杂度。

#### H5 降级技术实现

> **核心优势**：H5 降级页面复用 Taro H5 编译产物，**不需要额外开发**。同一个 React 组件在小程序端用原生组件渲染，在 H5 端用 DOM 渲染，功能天然完整。

**降级流程**：

```mermaid
sequenceDiagram
    participant MP as 小程序
    participant WV as web-view 组件
    participant H5 as H5 页面
    participant B as 后端

    MP->>MP: 用户点击"上传分析"等重功能
    MP->>B: GET /api/v1/auth/h5-token (JWT → 临时 token)
    B-->>MP: {token: "xxx", expire: 300s}
    MP->>WV: wx.navigateTo web-view 页面
    WV->>H5: 加载 https://h5.pingpongai.com/upload?token=xxx
    H5->>B: POST /api/v1/auth/h5-exchange {token} → JWT
    B-->>H5: {access_token}
    H5->>H5: 正常功能（大文件上传 / 3D 渲染 / 富文本编辑）
    H5->>WV: postMessage({action: "complete", result: {...}})
    WV->>MP: wx.miniProgram.postMessage → 触发回调
    MP->>MP: navigateBack + 刷新数据
```

**H5 降级页面清单（全 Phase）**

| 降级页面 | H5 功能 | 触发条件 | 上线阶段 |
|---------|---------|---------|---------|

## 5. 通信架构

### 5.1 REST API 模式

```
Client → POST/GET/PUT/DELETE /api/v1/{module}/{resource}
        ← {code: 200, message: "success", data: {...}, timestamp: "..."}
```

- **统一响应格式**：`app/core/response.py` → `success(data, message)` / `error(code, message)`
- **统一异常处理**：`app/core/exceptions.py` → `AppException(message, code, status_code)`
- **错误码体系**：系统采用 **HTTP 状态码 + 业务错误消息** 模式，不使用自定义 `ERR-XXX` 错误码。`AppException.code` 字段即 HTTP 状态码（如 404、409、422、429、503），`message` 为面向用户的中文错误描述。统一错误响应格式：`{code: <http_status>, message: <string>, data: null}`
  - **400** Bad Request：参数校验失败、业务逻辑校验失败（如退款金额超额）
  - **401** Unauthorized：未登录 / Token 过期
  - **403** Forbidden：权限不足（如免费用户访问会员功能、非管理员访问管理端）
  - **404** Not Found：资源不存在
  - **409** Conflict：状态冲突（如比赛不在进行中、订单已支付）
  - **422** Unprocessable Entity：请求体格式正确但语义错误（Pydantic 校验）
  - **429** Too Many Requests：限流触发（免费额度耗尽、API 请求频率超限）
  - **502** Bad Gateway：第三方服务不可用（微信下单失败、AI 推理服务不可用）
  - **503** Service Unavailable：服务降级中（熔断器打开、GPU 资源不足）
  - **500** Internal Server Error：未捕获的服务异常（自动上报 Sentry）
- **分页**：`app/core/pagination.py` → `paginate(query, page, page_size)` → `{total, page, page_size, items}`
- **API 文档**：FastAPI 自动生成 OpenAPI `/docs`（仅开发环境开放）

### 5.2 WebSocket 实时通信

```
Client → WS /api/v1/ws (Authorization: Bearer <JWT>)
         ← event: analysis_progress  data: {"task_id": "...", "step": 5, "total": 10, "message": "球体追踪中..."}
         ← event: analysis_complete   data: {"task_id": "...", "report_id": "..."}
         ← event: score_update        data: {"match_id": "...", "score": "11:8", "server": "player"}
         ← event: notification        data: {"type": "training_reminder", "content": "..."}
```

- **后端**：`app/api/v1/ws.py` → FastAPI WebSocket 端点
- **前端**：`src/utils/websocket.ts` → Taro WebSocket 封装（小程序用 wx.connectSocket，App 用 WebSocket）
- **用途**：
  - AI 分析进度实时推送（步骤式进度）
  - 记分牌实时同步（多设备观赛）
  - 训练提醒/系统通知推送
- **心跳**：30s 间隔，90s 无响应断开重连

### 5.3 异步任务队列模式

```
Client → POST /api/v1/video-analysis/tasks
        ← {code: 200, data: {"task_id": "task_xxx", "status": "queued"}}

[后台 Celery Worker 执行流水线]
  → Redis 队列消费 → AI 推理 → 结果聚合 → 存储 → WebSocket 通知
```

- **任务队列**：Redis broker + Celery
- **任务定义**：`app/services/ai_pipeline/tasks.py`
- **进度追踪**：每个 Step 完成后更新 Redis + PostgreSQL + WebSocket 推送
- **超时控制**：单个分析任务 600s 超时（`AI_ANALYSIS_TIMEOUT_SECONDS`）
- **重试策略**：失败步骤自动重试 2 次，指数退避

### 5.4 微信登录认证流程

```mermaid
sequenceDiagram
    participant C as Client (小程序)
    participant B as Backend (FastAPI)
    participant W as 微信开放平台
    participant D as PostgreSQL
    participant R as Redis

    C->>W: wx.login() → code
    W-->>C:临时登录凭证 code
    C->>B: POST /api/v1/auth/wechat-login {code}
    B->>W: code2session(code) → openid + session_key
    W-->>B: {openid, session_key}
    B->>D: 查询/创建 User (by openid)
    D-->>B: User record
    B->>B: 生成 JWT (access + refresh)
    B->>R: 存储 session_key (供后续解密)
    B-->>C: {access_token, refresh_token, user}

    Note over C: 后续请求携带 Bearer Token

            C->>B: GET /api/v1/xxx (Authorization: Bearer <JWT>)
    B->>B: 验证 JWT
    B-->>C: 200 Response

    C->>B: POST /api/v1/auth/refresh {refresh_token}
    B-->>C: {new access_token, new refresh_token}
```

### 5.5 微信支付流程

```mermaid
sequenceDiagram
    participant C as Client
    participant B as Backend (FastAPI)
    participant W as 微信支付
    participant D as PostgreSQL

    C->>B: POST /api/v1/orders {product_type, ...}
    B->>D: 创建订单 (status=pending)
    B->>W: 统一下单 (JSAPI/APP)
    W-->>B: prepay_id + 签名参数
    B-->>C: 支付参数 (prepay_id, paySign, ...)

    C->>W: 调起微信支付 (wx.requestPayment)
    W-->>C: 支付结果

    W->>B: 异步回调 /api/v1/payment/notify
    B->>B: 验签 + 解密
    B->>D: 更新订单 (status=paid)
    B->>B: 触发业务逻辑 (会员开通/分析额度/创作者收益)
    B-->>W: 200 (ACK)
    B->>C: WebSocket 推送支付成功
```

### 5.6 LLM 报告生成流程

```
[AI 流水线 Step 9: 报告生成]
  → 收集前 8 步结构化结果 (球轨迹/落点/动作/回合...)
  → 规则引擎查询知识库 (匹配问题模式 → 训练方法)
  → 组装 LLM Prompt (结构化数据 + 知识库上下文 + 用户画像)
  → 调用 LLM API (OpenAI 兼容)
  → 解析 LLM 输出 → 结构化报告 (JSON)
  → 存储 PostgreSQL (JSONB)
```

- **LLM 调用**：`app/services/ai_pipeline/report_generator.py`
- **Prompt 模板**：`app/services/knowledge_base/prompts/`
- **超时**：30s，失败降级为纯规则引擎输出
- **成本控制**：单次报告生成 LLM 调用预算 ¥0.1-0.3

### 5.8 通知分发策略

#### 通道选择矩阵

| 通知类型 | 用户在线 (WS) | 用户离线 (小程序) | 用户离线 (App) | 优先级 |
|---------|-------------|----------------|--------------|--------|
| AI 分析完成 | ✅ WebSocket 推送 | ✅ 微信订阅消息 | ✅ 推送通知 (APNs/FCM) | 高 |
| AI 分析失败 | ✅ WebSocket 推送 | ✅ 微信订阅消息 | ✅ 推送通知 | 高 |
| 记分牌实时同步 | ✅ WebSocket 推送 | ❌ 不推送 | ❌ 不推送 | 中 |
| 训练提醒 | ❌ 不推送 | ✅ 微信订阅消息 | ✅ 推送通知 | 低 |
| 支付成功 | ✅ WebSocket 推送 | ✅ 微信订阅消息 | ✅ 推送通知 | 高 |
| 系统/活动通知 | ❌ 不推送 | ✅ 微信模板消息 | ✅ 推送通知 | 低 |

#### 微信订阅消息管理

- **订阅模型**：微信小程序订阅消息为"一次性订阅"（每次用户操作时授权一次，发一条消耗一次）
- **授权时机**：用户点击"上传分析"时弹出订阅授权（分析完成通知）
- **长期订阅**：仅特定类目（教育/政务）可申请长期订阅，本项目暂不可用
- **降级**：订阅消息额度耗尽时，仅 WebSocket 推送，不补发

#### 训练提醒触发机制

- **Celery Beat 定时任务**：每日 19:00 检查"超过 3 天未训练的用户"
- **规则**：上次分析/记分距今 > 3 天 → 发送训练提醒
- **频率控制**：同一用户每周最多 2 次训练提醒
- **内容**：包含上次分析报告的训练建议摘要

### 5.9 OSS 直传完整流程

> 用户视频上传是整个产品的入口。采用 STS Token 临时授权直传 OSS 方案，客户端不经后端中转，减少带宽和延迟。

#### 完整时序

```mermaid
sequenceDiagram
    participant C as Client (小程序)
    participant B as Backend (FastAPI)
    participant O as OSS (阿里云)
    participant D as PostgreSQL

    C->>B: POST /api/v1/video-analysis/upload-token {filename, file_size}
    B->>B: 校验文件类型 (mp4/mov) + 大小 ≤ 500MB
    B->>B: 生成 OSS Key: videos/raw/{user_id}/{yyyymmdd}/{uuid}.mp4
    B->>O: 请求 STS Token (PutObject 权限, 15min 过期)
    O-->>B: STS 临时凭证 {AccessKeyId, AccessKeySecret, SecurityToken, Expiration}
    B->>D: 创建 file_record (status=uploading, oss_key, file_size, user_id)
    B-->>C: {file_id, upload_url, sts_credentials, oss_key, expire_at}

    Note over C: 小程序: wx.uploadFile (分片上传)
    Note over C: H5/App: OSS Multipart Upload

    C->>O: 直传视频文件 (PutObject / MultipartUpload, 携带 STS)
    O-->>C: 上传成功 (ETag)

    C->>B: POST /api/v1/video-analysis/upload-complete {file_id}
    B->>O: HEAD Object 确认文件存在 + Content-Length 匹配
    B->>D: 更新 file_record (status=uploaded, oss_etag, actual_size)
    B-->>C: {file_id, ready: true}

    C->>B: POST /api/v1/video-analysis/tasks {file_id, oss_key}
    B->>D: 创建 VideoTask (status=queued) + 消耗免费额度 (Redis DECR)
    B->>Celery: 入队分析任务
    B-->>C: {task_id, status: queued}
```

#### OSS 对象命名规范

| 文件类型 | OSS Key 格式 | 示例 | 说明 |
|---------|-------------|------|------|
| 原始视频 | `videos/raw/{user_id}/{yyyymmdd}/{uuid}.mp4` | `videos/raw/123/20261010/a1b2c3.mp4` | 用户上传的原始文件 |
| 标准化视频 | `videos/standard/{task_id}/standard.mp4` | `videos/standard/task_xxx/standard.mp4` | FFmpeg 转码后 1080p/30fps |
| 标注视频 | `videos/annotated/{task_id}/annotated.mp4` | `videos/annotated/task_xxx/annotated.mp4` | AI 流水线 Step 10 产出 |
| 多清晰度版本 | `videos/adaptive/{task_id}/{quality}.mp4` | `videos/adaptive/task_xxx/720p.mp4` | 720p/480p 降清版本 |
| 封面图 | `images/covers/{task_id}/cover.jpg` | `images/covers/task_xxx/cover.jpg` | 第 1 秒截帧 |
| 报告图片 | `images/reports/{task_id}/{chart_name}.png` | `images/reports/task_xxx/heatmap.png` | 报告内图表 |
| 3D 模型 | `models/3d/{category}/{model_id}_v{version}.glb` | `models/3d/forehand/m001_v2.glb` | 版本化 URL，更新即新文件 |
| 用户头像 | `images/avatars/{user_id}_v{timestamp}.jpg` | `images/avatars/123_v1696900000.jpg` | 更新加版本戳 |
| 创作者视频 | `videos/creator/{creator_id}/{video_id}.mp4` | `videos/creator/c456/v789.mp4` | Phase 3 UGC 视频 |

> **命名约束**：所有 Key 使用 UUID 或时间戳，不含用户原始文件名（防止信息泄露和特殊字符问题）。`{user_id}` 便于按用户查询和清理。

#### 大文件上传策略

| 端 | 上传方式 | 说明 |
|----|---------|------|
| 微信小程序 | `wx.uploadFile`（单次上传，≤ 500MB） | 小程序不支持 Multipart Upload；500MB 以内单次上传可接受，弱网下有失败重试 |
| H5 (web-view) | OSS Multipart Upload | 分片上传，每片 5MB，支持断点续传 |
| App (RN) | OSS Multipart Upload | 同 H5，分片 + 断点续传 |

> **小程序弱网降级**：`wx.uploadFile` 失败后自动重试 3 次（指数退避 1s/2s/4s）。3 次失败提示用户"网络不稳定，请切换 WiFi 后重试"。已上传部分不保留（小程序限制），需重新上传。

#### 孤儿文件清理

- **场景**：用户获取了 STS Token 并上传了文件，但未调用 `upload-complete`（关闭 App / 网络中断）
- **清理机制**：Celery Beat 定时任务每小时扫描 `file_record` 表
  - `status=uploading` 且 `created_at` 超过 1 小时 → 标记为 `abandoned`
  - 对应 OSS 文件由 OSS Lifecycle 规则自动删除（见 12.10 节）
- **STS Token 过期保护**：STS Token 15 分钟过期，过期后无法继续上传，自然限制孤儿文件产生窗口

### 5.10 WebSocket 连接管理与重连策略

> WebSocket 承载 AI 分析进度推送和记分牌实时同步，连接稳定性直接影响核心用户体验。

#### 客户端连接生命周期

```mermaid
graph TB
    subgraph WSLifecycle["WebSocket 连接生命周期"]
        Connect["建立连接<br/>(携带 JWT)"]
        AuthOK{"JWT 有效?"}
        Connected["连接就绪<br/>(加入用户频道)"]
        Heartbeat["心跳保活<br/>(30s ping)"]
        Lost["连接断开"]
        Backoff["指数退避重连<br/>(1s→2s→4s→8s→16s)"]
        MaxRetry{"重试 < 5 次?"}
        Reconnected["重连成功"]
        GiveUp["放弃重连<br/>(提示用户网络异常)"]
    end

    Connect --> AuthOK
    AuthOK -->|是| Connected
    AuthOK -->|否| RefreshToken["刷新 JWT"]
    RefreshToken --> Connect
    Connected --> Heartbeat
    Heartbeat -->|90s 无响应| Lost
    Heartbeat -->|正常| Connected
    Lost --> Backoff
    Backoff --> MaxRetry
    MaxRetry -->|是| Reconnected
    Reconnected -->|成功| Connected
    Reconnected -->|失败| Backoff
    MaxRetry -->|否| GiveUp
```

#### 频道与房间管理

| 频道/房间 | Key 格式 | 用途 | 订阅时机 |
|-----------|---------|------|---------|
| 用户频道 | `ws:user:{user_id}` | AI 分析进度、支付结果、系统通知 | 用户连接 WebSocket 时自动加入 |
| 比赛房间 | `ws:match:{match_id}` | 记分牌实时同步 | 用户进入记分牌页面时加入，离开时退出 |

> 后端使用 Redis 维护 `ws:user:{user_id}` → `[{connection_id, ...}]` 映射，支持多设备同时在线。比赛房间同理，多设备订阅同一 `match_id`。

#### 断连期间消息补偿

| 场景 | 补偿策略 |
|------|---------|
| AI 分析完成时用户断连 | 消息写入 `notification_record` 表，用户重连后拉取离线消息（HTTP + WS 双通道） |
| 记分牌比分更新时某设备断连 | 重连后发送 `sync_match` 全量同步事件（当前比分 + 比分序列 + 比赛状态） |
| 系统通知 | 写入 `notification_record`，重连后通过 HTTP API `/notification/list` 拉取 |

#### 消息顺序保证

- **分析进度**：每个 Step 携带 `step` 序号（1-10），客户端按序号展示，乱序时丢弃旧序号消息
- **记分牌比分**：每条 `score_update` 携带 `sequence` 字段（全局递增），客户端检测到序号跳跃时触发 `sync_match` 全量同步
- **单连接内有序**：单条 WebSocket 连接内消息天然有序（TCP 保证）；跨重连不保证顺序，靠序号 + 全量同步补偿

#### Token 无感刷新

```
WS 连接建立时 JWT 有效 → 心跳期间 access_token 过期（120min）
  → 后端 WS 心跳响应中携带 token_expired: true 标记
  → 客户端暂停心跳，调用 POST /auth/refresh 获取新 access_token
  → 带新 token 重新建立 WS 连接（旧连接自动关闭）
  → 重连后触发 sync_match / sync_analysis 全量状态同步
```

#### 连接扩容方案

| 阶段 | 方案 | 说明 |
|------|------|------|
| Phase 1 | 单实例（FastAPI WebSocket） | 同时连接 < 5000，单 Uvicorn worker 够用 |
| Phase 2+ | Nginx WebSocket 代理 + 多实例 | Nginx `upstream` + `proxy_pass` 负载均衡，Redis 维护连接→实例映射 |
| Phase 5 | 独立 WS 网关 | 连接数 > 10000 时拆分为独立 WebSocket 服务，通过 Redis Pub/Sub 与主业务通信 |

## 6. AI 视频分析流水线设计

### 6.1 流水线步骤详解

| 步骤 | 名称 | 模型/算法 | 输入 | 输出 | 预估耗时 | GPU 需求 | Phase 归属 |
|------|------|----------|------|------|---------|---------|----------|
| 1 | 视频预处理 | FFmpeg | 原始视频 (OSS) | 标准化帧序列 (30fps, 1080p) | 10-30s | CPU | Phase 1 完整实现 |

| 3 | 球体检测 | TTNet / TrackNetV5 | 连续 9 帧拼接 | 球位置 heatmap → 坐标序列 | 30-120s | GPU (T4) | Phase 1 完整实现 |
| 4 | 球体追踪 | 卡尔曼滤波 + 抛物线模型 | 球坐标序列 + 弹跳事件 | 连续球轨迹 + 球速估算 | 10-30s | CPU/GPU | Phase 1 占位骨架 / Phase 2+ 完整实现 |
| 5 | 落点估算 | 单应性矩阵映射 | 球轨迹 + 球台坐标 | 落点九宫格分布 | 5-10s | CPU | Phase 1 占位骨架 / Phase 2+ 完整实现 |

| 8 | 回合分割 | 弹跳事件 + 节奏分析 | 球轨迹 + 动作序列 | 回合边界 + 得分归属 | 5-15s | CPU | Phase 1 占位骨架 / Phase 2+ 完整实现 |
| 9 | 报告生成 | 规则引擎 + LLM | 全部结构化结果 + 知识库 | 分析报告 (JSON + 文字) | 10-30s | CPU | Phase 1 完整实现 |

> **GPU 成本**：T4 实例 ~1.87 元/小时，单次分析 GPU 成本 ~0.1-0.3 元
>
> **Phase 归属说明（R19-P3-1 修复）**：
> - Phase 1 流水线**端到端可跑通**（编排 + 进度追踪 + 级联链路 _trigger_cascade + WebSocket 推送 + 失败回退），step_4/5/6/8 在 Phase 1 仅占位骨架（`pass # 占位实现`），step_9 报告生成与 step_10 标注视频在 Phase 1 完整实现
> - Phase 1 MVP 上线时 step_4/5/8 占位步骤返回空结果集，step_6 仅 MediaPipe 基础关键点，step_7 动作识别为空（Temporal CNN 模型待 Phase 2 训练），分析报告以 step_1~3/9/10 的规则引擎 + LLM 文字生成为主
> - Phase 2+ 完整补齐：卡尔曼滤波球体追踪（含球速估算）、单应性矩阵落点九宫格、MMPose 姿态增强、Temporal CNN 动作分类、弹跳事件 + 节奏分析回合分割
> - **R19 验证（§3.2 + §6.1）**：10 步流水线 Phase 归属列完整，step_1/2/3/9/10 属 Phase 1 完整实现，step_4~8 属 Phase 2+（其中 step_6 为 Phase 1 基础 + Phase 2+ 增强，step_7 为 Phase 2 完整实现）

### 6.4 视频转码策略

> 用户上传视频格式/分辨率/帧率不一，AI 分析和 CDN 分发需标准化处理。

#### 标准化输入格式（送入 AI）

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 编码格式 | H.264 (libx264) | 通用兼容 |
| 容器格式 | MP4 | 标准 |
| 分辨率 | 1920×1080 (1080p) | 过高分辨率降采样，过低则保持原样 |
| 帧率 | 30 fps | 高帧率抽帧降至 30fps，低帧率保持原样 |
| 音频 | 移除 | AI 分析不需要音频 |

> 转码命令示例：`ffmpeg -i input.mov -vf scale=1920:1080 -r 30 -an -c:v libx264 -preset fast -crf 23 output_standard.mp4`

#### 多清晰度输出（CDN 分发）

| 清晰度 | 分辨率 | 码率 | 用途 |
|--------|--------|------|------|
| 原画 | 原始 | 原始 | 下载/高质量回看 |
| 1080p | 1920×1080 | 4Mbps | WiFi 播放 |
| 720p | 1280×720 | 2Mbps | 4G 播放 |
| 480p | 854×480 | 1Mbps | 弱网播放 |

### 9.2 JSONB 字段存储策略

| 表 | JSONB 字段 | 内容结构 | 查询方式 |
|----|----------|---------|---------|
| `analysis_report` | `result_data` | 第 6.3 节定义的完整分析结果 JSON | 整体读取，不索引 |
| `analysis_report` | `report_text` | `{summary, issues[], suggestions[]}` | GIN 索引（按问题关键词搜索） |
| `user` | `equipment_config` | `{blade: {...}, rubber_fh: {...}, rubber_bh: {...}, shoes: "..."}` | 整体读取 |
| `knowledge_entry` | `content` | 知识库条目结构化数据（动作要点/常见错误/训练方法） | GIN 索引 |
| `rule_definition` | `condition` | `{field, operator, threshold}` | 服务端解析，不索引 |
| `rule_definition` | `diagnosis` | `{problem_id, problem_name, severity, description}` | 整体读取 |
| `training_template` | `template_data` | `{goal, sessions[], exercises[], metrics[]}` | 整体读取 |
| `match_statistic` | `stats_data` | `{score_distribution, key_points, technique_breakdown}` | 整体读取 |
| `progress_snapshot` | `metrics_snapshot` | `{backhand_ratio: 0.25, forehand_ratio: 0.68, landing_dispersion: 3.2, ...}` | GIN 索引（按指标查询） |
| `technique_trend` | `time_series` | `[{date: "2026-07-10", value: 0.18}, ...]` | 整体读取 |
| `plan_adjustment` | `old_plan_snapshot` / `new_plan_snapshot` | 训练方案完整快照（目标/内容/量/检验） | 整体读取 |
| `badge_definition` | `condition` | `{metric, operator, threshold}` | 服务端解析，不索引 |

> **F5-3 徽章触发条件规范**：`badge_definition.condition` 字段定义徽章自动授予的判定逻辑，格式为 `{metric: string, operator: string, threshold: number}`：
> - `metric`：判定指标名，取值范围：`total_analyses`（累计分析次数）、`win_count`（累计胜场）、`training_streak_days`（连续训练天数）、`landing_improvement`（落点分散度提升值）、`backhand_ratio`（反手使用率）
> - `operator`：比较运算符，取值范围：`>=`、`<=`、`>`、`<`、`==`
> - `threshold`：阈值数值（如 `total_analyses >= 10` 表示累计分析满 10 次自动授予徽章）
> - 判定时机：每次分析报告生成后，由 gamification 模块的 Celery 任务批量检查所有未获得徽章的 `condition` 是否满足

> **GIN 索引策略**：对需要按 JSONB key 查询的字段（如 `report_text.issues`、`knowledge_entry.content`）创建 GIN 索引。对整体读取的字段不索引，避免写入性能下降。

| `feedback_record` | ~150/月 | 不分区 | 永久保留（数据飞轮核心资产） |
| `progress_snapshot` | ~500/月（每次分析生成一条） | 不分区 | 永久保留（趋势分析基础数据） |
| `technique_trend` | ~9000/月（500 用户 × 18 指标） | 不分区 | 永久保留（更新而非新增） |
| `plan_adjustment` | ~50/月 | 不分区 | 永久保留（方案调整历史） |

> **分区实现**：使用 PostgreSQL 原生声明式分区，Alembic 迁移中创建分区表。每月初通过 `pg_cron` 自动创建下月分区。

## 12. 专项算法设计

### 12.1 乒乓大数据——间接胜利算法

> 需求：A 战胜 B，B 战胜 C → A "间接战胜" C。展示"间接战胜马龙/孙颖莎"等趣味数据。

#### 问题描述

间接胜利是一个有向图可达性问题。全图 BFS/DFS 随用户量增长计算成本极高（O(V+E)），不可实时计算。

#### 设计方案：预计算 + 缓存 + 深度限制

```mermaid
graph TB
    MatchFinish["比赛结束<br/>(A 战胜 B)"]
    TriggerUpdate["触发异步更新任务<br/>(Celery task)"]
    BFS["受限 BFS<br/>(从 A 出发，沿胜利边遍历<br/>最多 4 层)"]
    UpdateRedis["更新 Redis 缓存<br/>(A 的间接胜利集合)"]
    UpdateDB["更新 PostgreSQL<br/>(间接战胜最高分/名人列表)"]

    MatchFinish --> TriggerUpdate
    TriggerUpdate --> BFS
    BFS --> UpdateRedis
    UpdateRedis --> UpdateDB
```

| 参数 | 值 | 说明 |
|------|-----|------|
| 最大遍历深度 | 4 层 | A→B→C→D→E，覆盖绝大多数有意义路径 |
| 缓存 Key | `big_data:user:{user_id}` | Redis Hash |
| 缓存 TTL | 24h | 过期后下次查询重新计算 |
| 计算触发 | 比赛结束后异步 Celery 任务 | 不阻塞比赛记分流程 |
| 名人匹配 | 预置名人积分 ID 列表（马龙/孙颖莎等国手开球网 ID） | 匹配间接胜利集合中的名人 ID |

> **降级策略**：用户量 < 1000 时可全量计算；用户量增长后深度限制为 4 层 + 缓存。极端情况下（图过大）仅计算 3 层。

### 12.2 智能组队算法（Phase 4）

> 需求：现场活动按开球网积分智能匹配队伍，保证实力平均。

#### 蛇形分配算法

```
输入：N 名球员，按积分降序排序 [P1, P2, P3, ..., PN]
目标：分成 K 队，每队实力尽可能平均

算法（蛇形分配）：
  第 1 轮：P1→队1, P2→队2, ..., PK→队K
  第 2 轮：P(K+1)→队K, P(K+2)→队(K-1), ..., P(2K)→队1  （反向）
  第 3 轮：P(2K+1)→队1, P(2K+2)→队2, ...
  ...依此类推

结果：每队积分总和尽可能接近
```

| 参数 | 说明 |
|------|------|
| 时间复杂度 | O(N log N)（排序）+ O(N)（分配），现场秒级完成 |
| 积分来源 | 用户开球网积分（`user.kqs_rating`） |
| 人数不等时 | 人数不能整除 K 时，部分队伍多 1 人 |
| 手动调整 | 组队结果展示后，组织者可手动微调（拖拽换人） |

### 12.3 搜索服务架构

| 阶段 | 方案 | 适用场景 |
|------|------|---------|
| Phase 1-2 | PostgreSQL 全文搜索（`tsvector` + `GIN` 索引） | 分析报告搜索、训练模板搜索 |
| Phase 3+ | Meilisearch（轻量搜索引擎） | 社区帖子/视频/球馆/装备全文搜索 |

> **选型理由**：Meilisearch 比 Elasticsearch 更轻量（单二进制部署），适合个人开发者。支持中文分词、模糊搜索、 typo-tolerance。Phase 3 社区上线后内容量增长，PG 全文搜索性能不足时引入。

### 12.5 嵌入式视频模式方案（Phase 3）

> 学习视频三种模式中"嵌入模式"的技术实现。

| 模式 | 实现方案 | 技术细节 |
|------|---------|---------|
| 嵌入模式 | iframe 嵌入第三方播放器（B站/抖音/YouTube） | 仅存储外链 URL + 元数据，不下载不重新托管 |
| 授权本地化 | 下载到 OSS + 平台播放器 | 创作者授权后下载，CDN 分发，支持慢放/逐帧 |
| UGC | 用户上传到 OSS + 平台播放器 | 创作者直接上传，需审核后上线 |

#### 嵌入模式技术细节

- **iframe 播放器**：B站 `//player.bilibili.com/player.html?bvid=xxx`，抖音/YouTube 各有嵌入 API
- **外链可用性监控**：每日定时任务检查嵌入视频外链是否有效（HTTP HEAD 请求），失效则标记"视频已下架"
- **信息流统一展示**：嵌入视频在社区信息流中与平台内视频统一展示，缩略图 + 来源标注（"来自B站"）
- **版权声明**：嵌入页面底部标注"本视频来自 {平台}，版权归原作者所有"
- **跟练模式**：嵌入模式不支持跟练（无法控制播放器速度），仅授权本地化和 UGC 支持

### 12.6 CDN 缓存策略

| 资源类型 | CDN 缓存 TTL | 缓存失效策略 | 回源比例 |
|---------|-------------|-------------|---------|
| 3D 模型 (GLB) | 1 年 | 版本化 URL（`model_v2.glb`），更新即新 URL | <1% |
| 标注视频 | 30 天 | 报告删除时 CDN 缓存自然过期 | <5% |
| 用户头像 | 7 天 | 用户更新头像 → URL 加 `?v=timestamp` 参数 | <10% |
| 分析报告图片 | 30 天 | 不更新（历史快照） | <1% |
| 前端静态资源 | 1 年 | 文件名 hash 化（`app.a3f8b2.js`），发布即新文件 | <1% |
| 教学视频缩略图 | 30 天 | 创作者更新 → CDN 刷新 API 主动刷新 | <5% |

> **缓存刷新**：头像/缩略图等用户可变资源，更新后调用 CDN 刷新 API（阿里云 `RefreshObjectCaches`）主动刷新。

#### 趋势计算规则

| 趋势类型 | 判定条件 | 建议生成策略 |
|---------|---------|------------|
| 📈 改善中 | 连续 ≥ 2 次分析，指标向目标值靠近，变化率 > 5% | "进步确认 + 维持当前方案" |
| ➡️ 停滞 | 连续 ≥ 3 次分析，指标变化率 < 5%，未达目标 | "停滞警告 + 调整方案/增加训练量" |

| 🆕 新问题 | 最新报告中出现但历史报告中未出现过的问题 | "新问题识别 + 针对性建议" |
| 🔄 已解决 | 历史报告中存在但最近 2 次报告中消失的问题 | "问题已改善 + 确认/巩固建议" |

#### 训练负荷分析（Phase 2 增强）

> 需求 v0.4 Phase 2 提到"训练负荷分析（训练量与水平变化关联）"。此功能作为 `monthly_report` 的增强能力，不单独建模块。

| 分析维度 | 数据来源 | 计算方式 | 输出 |
|---------|---------|---------|------|
| 训练频次 | `progress_snapshot` 按月聚合 | 月度分析次数 + 记分比赛次数 | 月度训练日历热图 |
| 训练量趋势 | `technique_trend` + `match_record` | 对比近 3 月训练频次变化率 | 上升/持平/下降 |
| 负荷-水平关联 | 训练频次 × `kqs_rating` 变化 | Pearson 相关系数（训练量 vs 积分变化） | 相关系数 + 散点图数据 |
| 建议 | 上述分析结果 | 低频次+积分停滞 → "增加训练量"；高频次+进步 → "维持当前节奏" | 月度报告中的负荷建议段落 |

> **实现**：月度报告生成时（Celery 定时任务，每月 1 日），从 `progress_snapshot` 和 `rating_history` 聚合上月数据，计算 Pearson 相关系数。相关系数 |r| < 0.3 视为无显著关联，0.3-0.5 弱关联，> 0.5 强关联。

#### 趋势预测（Phase 2 增强）

> 需求 v0.4 Phase 2 提到"趋势预测（基于历史数据预测水平变化趋势）"。此功能基于 `technique_trend` 时间序列做简单线性外推，非 ML 模型。

```mermaid

    Target{"达到目标值?"}

    Plateau["停滞预警<br/>'当前进步速率接近 0，建议调整方案'"]
    Decline["退步预警<br/>'指标呈下降趋势，建议关注'"]

    History --> Regression
    Regression --> Extrapolate
    Extrapolate --> Target
    Target -->|是| Forecast
    Target -->|斜率≈0| Plateau
    Target -->|斜率<0| Decline
```

| 参数 | 值 | 说明 |
|------|-----|------|
| 最小数据点 | 3 个快照 | 不足 3 个无法做回归，提示"数据不足" |
| 预测窗口 | 4 周 | 短期预测，不外推过远（避免失真） |
| 回归方法 | 最小二乘法线性回归 | `numpy.polyfit(x, y, 1)` |
| 预测展示 | "按当前进步速率，预计 X 周后达到目标值" | 展示在月度报告 + 进度摘要中 |
| 置信度 | R² > 0.7 时标注"高置信度"，0.4-0.7 "中等置信度"，< 0.4 不展示预测 | 避免低质量预测误导用户 |

> **API 集成**：`GET /progress/summary` 返回中增加 `forecast` 字段（`{metric, current_value, target, predicted_weeks_to_target, confidence}`），仅在 R² > 0.4 时填充。`GET /monthly-report/{id}` 返回中增加 `training_load` 字段（训练频次 + 负荷关联 + 建议）。

| `finished` | 查看统计、分享报告 | 记分、撤销 | 已生成 MatchStatistic |
| `abandoned` | 恢复（24h 内）、删除 | 记分 | 中途放弃，保留比分序列 |

> **状态守卫**：后端 API 层强制状态校验。`POST /scoring/matches/{match_id}/score` 仅在 `in_progress` 状态下允许；`POST /scoring/matches/{match_id}/finish` 仅在 `in_progress` 状态下允许。

#### 多设备同步协议

```mermaid
sequenceDiagram
    participant A as 设备 A (记分者)
    participant B as Backend
    participant R as Redis
    participant W as 设备 B (观赛者)

    Note over A,W: 两台设备同时观看同一场比赛

    A->>B: POST /scoring/matches/{match_id}/score {scorer, method}
    B->>R: Redis 原子操作: score_seq = INCR match:{id}:seq
    B->>R: 写入 score_record (seq, scorer, method, timestamp)
    B->>R: 更新 match:{id}:current_score 缓存
    B-->>A: 200 {sequence: N, score: "11:8"}

    B->>W: WS event: score_update {match_id, sequence: N, score: "11:8", scorer, method, timestamp}

    Note over W: 设备 B 收到推送，更新本地记分牌

    W->>W: 本地 sequence = N-1 → 收到 N → 顺序正确，更新

    Note over A,W: 设备 B 短暂断连后重连

    W->>B: WS reconnect → 加入 ws:match:{id}
    B->>R: 读取 match:{id}:current_score + 最近 N 条 score_record
    B->>W: WS event: sync_match {match_id, status, current_score, score_sequence: [...], last_update}
    Note over W: 全量同步，覆盖本地状态
```

#### 并发记分冲突处理

| 策略 | 实现 | 说明 |
|------|------|------|
| 序号原子生成 | Redis `INCR match:{id}:seq` | 确保每球序号全局唯一递增，不可能重复 |
| 写入顺序 | 先 INCR 取序号 → 再写 score_record | 序号决定比分顺序，与请求到达先后无关 |
| 客户端展示 | 按 `sequence` 排序展示 | 客户端收到 `score_update` 后按序号插入/更新 |

> **设计决策**：不做乐观锁 / CAS。乒乓球比赛记分是单操作者为主（一个人主记，另一人观赛），极少出现同时记分。即使同时记分，序号保证了全局一致性，两球都有效（只是顺序可能不同于用户预期，可撤销修正）。

#### 撤销跨设备同步

```mermaid
graph LR
    Undo["设备 A 撤销<br/>POST /scoring/matches/{match_id}/undo"]
    CheckSeq{"最新球 seq ==<br/>本地记录?"}
    DeleteLast["删除最后一条<br/>score_record"]
    UpdateRedis["更新 current_score<br/>(回退到 seq-1)"]
    PushUndo["WS push: score_update<br/>{sequence: N-1, action: undo, score}"]
    RejectUndo["拒绝撤销<br/>(告知用户已被覆盖)"]

    Undo --> CheckSeq
    CheckSeq -->|是| DeleteLast
    CheckSeq -->|否| RejectUndo
    DeleteLast --> UpdateRedis
    UpdateRedis --> PushUndo
```

> **撤销约束**：仅允许撤销最后 1 球（`seq == max_seq`）。如果另一设备在撤销前又记了一球（`max_seq` 已变化），撤销请求被拒绝，提示"比分已更新，请确认后撤销"。撤销成功后推送 `score_update` 事件（`action: undo`），所有设备同步回退。

#### 比赛恢复机制

- **场景**：App 崩溃 / 手动退出后重新进入比赛
- **恢复流程**：`GET /scoring/matches/{match_id}` 返回完整状态（status、current_score、score_sequence、last_update_at）
- **24h 窗口**：`abandoned` 状态的比赛 24h 内可恢复为 `in_progress`，超过 24h 不可恢复
- **全量同步**：恢复后通过 `sync_match` WebSocket 事件同步全部比分序列

#### 发球轮换规则

> F2-2 修复：补充发球轮换规则，与记分逻辑和前端展示对齐。

- **初始发球**：比赛创建时由 `current_server` 字段记录初始发球方（用户在 setup 阶段选择）
- **轮换规则（11 分制）**：
  - 每 2 球轮换一次发球权（即 `sequence % 2 == 1` 时保持当前发球方，`sequence % 2 == 0` 时切换发球方）
  - **deuce（10:10）后**：每 1 球轮换一次发球权
- **赛制差异（bo3/bo5/bo7）**：每局开始时，发球方为上一局末尾发球方的对手（如局1 A 发球→局2 B 发球→局3 A 发球，交替开局）
- **前端展示**：记分牌页面实时显示 `current_server` 图标（🏓 在发球方一侧）
- **后端实现**：记分 API（`POST /scoring/matches/{match_id}/score`）在处理记分请求时自动更新 `match:{id}:current_server` Redis 缓存，并通过 `score_update` WebSocket 事件推送最新发球方

### 12.9 订阅续费与权益到期机制

> 会员订阅涉及收入，需明确续费方式、到期检测和权益降级逻辑。

#### 订阅生命周期

```mermaid
graph LR
    subgraph SubLifecycle["订阅生命周期"]
        Active["active<br/>(有效期内)"]
        ExpiringSoon["expiring_soon<br/>(到期前 3 天)"]
        Expired["expired<br/>(已到期)"]
        GracePeriod["grace_period<br/>(宽限期 7 天)"]
        Closed["closed<br/>(彻底过期)"]
    end

    Active -->|"到期前 3 天"| ExpiringSoon
    ExpiringSoon -->|"到期日到达"| Expired
    Expired -->|"自动续费成功"| Active
    Expired -->|"未续费"| GracePeriod
    GracePeriod -->|"7天内续费"| Active
    GracePeriod -->|"7天后"| Closed
    Closed -->|"重新订阅"| Active
```

#### 续费方式

| 方式 | 实现 | 说明 |
|------|------|------|
| 手动续费（默认） | 到期后用户主动购买，微信支付 JSAPI 一次性付款 | Phase 1 采用，简单可靠 |
| 自动续费（Phase 2+） | 微信支付委托代扣（签约扣款），到期前 1 天自动扣费 | 需用户签约授权，扣费失败降级为手动续费 |

> **Phase 1 决策**：采用手动续费。自动续费需签约流程复杂（微信支付代扣签约），且用户对自动扣费敏感，Phase 1 优先简单可靠。到期前 3 天通过微信订阅消息提醒用户续费。

#### 到期检测机制

- **Celery Beat 定时任务**：每日 00:30 扫描 `subscription` 表
  - `expire_at` 在未来 3 天内 + `status=active` → 标记 `expiring_soon`，发送续费提醒
  - `expire_at` 已过期 + `status=active/expiring_soon` → 标记 `expired`，触发权益降级
  - `expire_at` 过期超 7 天 + `status=expired` → 标记 `closed`
- **实时校验（兜底）**：每次请求会员功能时检查 `subscription.expire_at`，过期则拒绝（防止 Celery 延迟）

#### 权益到期后的数据访问策略

| 数据类型 | 到期后访问 | 说明 |
|---------|----------|------|
| 历史分析报告（JSONB） | ✅ 只读可见 | 用户已产生的数据不收回，但不可新建分析（免费额度 3/天） |
| 标注视频 / CDN | ✅ 30 天内可见 | 到期 30 天后 CDN 缓存自然过期，OSS 按留存策略处理 |
| 训练方案 / 训练单 | ✅ 只读可见 | 已生成的方案保留，不可生成新方案 |
| 3D 教学内容 | ❌ 不可访问 | 会员专属内容，到期后入口隐藏 |
| 进度分析 / 趋势对比 | ❌ 不可访问 | 会员专属功能，到期后入口隐藏 |
| 数据看板 | ✅ 基础可见 | 胜率/比赛记录可见；落点热图/技术统计降级为不可用 |

> **设计原则**：用户产生的数据（报告/比赛记录/训练方案）永远可见，会员专属功能（3D/高级分析/趋势对比）到期后不可用。降级而非删除，激励用户续费恢复完整体验。

#### 免费额度计数器机制

| 机制 | 实现 | 说明 |
|------|------|------|
| 计数 Key | `quota:analysis:{user_id}:{yyyymmdd}` | Redis String，值为今日已用次数 |
| 初始值 | 不预创建，首次 `GET /membership/quota` 时惰性初始化 | `FREE_ANALYSIS_DAILY_LIMIT - used = remaining` |
| 原子扣减 | `INCR quota:analysis:{user_id}:{date}` 后判断是否超限 | 防止并发请求绕过额度 |
| 自动重置 | Redis Key 设置 TTL 至次日 00:00:00 + 1h | 自然过期，次日自动从 0 开始，无需 Celery |
| 回退（额度耗尽） | `INCR` 后超限则 `DECR` 回退，返回 403 提示购买会员 | 确保不误扣 |

#### 会员升级流程

- **升级路径**：免费 → 会员 → 专业用户 → 教练用户
- **补差价逻辑**：当前订阅未到期时升级，按剩余天数比例计算差价
  - `差价 = 新套餐日均价格 × 剩余天数 - 旧套餐日均价格 × 剩余天数`
  - 剩余天数 < 7 天时不支持补差升级，建议到期后直接购买新套餐
- **降级**：到期后自然降级为免费用户，不支持主动降级退款

### 12.11 数据看板预计算策略

> 数据看板聚合跨多次分析报告和比赛记录的统计。需明确哪些实时计算、哪些预计算，避免查询性能瓶颈。

#### 预计算 vs 实时计算决策矩阵

| 看板项 | 数据来源 | 策略 | 缓存 TTL | 理由 |
|--------|---------|------|---------|------|
| 概览卡片（胜率/分析次数/训练频次） | 聚合查询 | Redis 缓存 | 5min | 数据变化低频，缓存可接受 5min 延迟 |
| 战绩趋势（折线图） | match_record 聚合 | Redis 缓存 | 1h | 历史数据不变，新比赛后主动 bust |
| 技术统计（环形图） | analysis_report JSONB | Redis 缓存 | 1h | 新分析后主动 bust |
| 累计落点热图 | 多报告 JSONB 聚合 | **预计算物化视图** | 1h | 跨多次报告聚合，实时计算代价高 |
| 比赛记录列表 | match_record 分页查 | 实时查询 | 不缓存 | 分页查询，结果随翻页变化 |

#### 累计落点热图预计算方案

```mermaid
graph LR
    subgraph Trigger["触发时机"]
        NewReport["新分析报告完成"]
        ReportDelete["报告被删除"]
    end

    subgraph Precompute["预计算流程"]
        ReadReports["读取用户全部报告<br/>result_data.landing_points"]
        AggregateGrid["聚合九宫格计数<br/>(所有报告叠加)"]
        AggregateDist["聚合落点分布<br/>(正手/反手/中区占比)"]
        WriteRedis["写入 Redis<br/>dashboard:heatmap:{user_id}"]
    end

    NewReport --> ReadReports
    ReportDelete --> ReadReports
    ReadReports --> AggregateGrid --> AggregateDist --> WriteRedis
```

| 参数 | 值 | 说明 |
|------|-----|------|
| 缓存 Key | `dashboard:heatmap:{user_id}` | Redis Hash |
| 缓存结构 | `{nine_grid: [[...]], distribution: {...}, total_rallies: N}` | 聚合后的热图数据 |
| 触发方式 | Celery 异步任务（分析完成后触发） | 不阻塞分析流水线 |
| 缓存 TTL | 1h | 兜底过期；正常通过主动 bust 保持新鲜 |
| 降级 | 缓存未命中时实时计算（限制最近 10 次报告） | 报告多时实时聚合慢，限制范围 |

#### 缓存失效策略

| 事件 | 需要 bust 的缓存 | 方式 |
|------|-----------------|------|
| 新分析报告完成 | `dashboard:overview:{user_id}`, `dashboard:technique:{user_id}`, `dashboard:heatmap:{user_id}` | Redis DEL（分析完成回调中执行） |
| 新比赛结束 | `dashboard:overview:{user_id}`, `dashboard:winrate:{user_id}` | Redis DEL（比赛结束回调中执行） |
| 报告被删除 | 同分析完成 | Redis DEL |
| 用户切换时间范围 | 无（时间范围作为查询参数，不缓存） | — |

> **设计原则**：写入时主动 bust 相关缓存，读取时缓存未命中则实时计算并回填缓存。不使用物化视图（PostgreSQL 物化视图刷新成本高，Redis 预计算更灵活）。

### 12.13 创作者收益计算与提现流程 (Phase 3)

> 创作者经济是 Phase 3 核心商业闭环。需明确收益计算模型、提现流程和退款影响。

#### 收益计算模型

| 收益来源 | 计算方式 | 创作者分成 | 平台抽成 |
|---------|---------|----------|---------|
| 单次购买 | 用户支付金额 × 80% | 80% | 20% |
| 会员观看 | 按播放次数分摊（月度结算） | 75% | 25% |

> **Anti-Hallucination 约束**：创作者分成不低于 75-80%，平台抽 20-25%。单次购买分成 80%，会员观看分成 75%（平台需承担会员获取成本）。

### 12.15 开球网对接降级策略 (Phase 4)

> 开球网 API 是外部依赖，需设计降级方案确保核心功能不受影响。

#### 降级矩阵

| 场景 | 正常流程 | 降级流程 | 触发条件 |
|------|---------|---------|---------|
| 积分同步 | 自动拉取开球网积分 | 用户手动输入积分 | API 不可用 / 用户无开球网账号 |
| 赛事报名 | 通过平台报名并同步开球网 | 仅平台内部记录 | API 不可用 |
| 排名查询 | 实时同步开球网排名 | 展示缓存排名（标注"数据更新时间"） | API 不可用 |
| 积分历史 | 拉取开球网历史变动 | 仅展示平台内记录的比赛 | API 不可用 |

#### 用户无开球网账号处理

```mermaid
graph LR
    UserReg["用户注册/个人档案"]
    HasKQS{"已绑定开球网?"}
    AutoSync["自动同步积分/排名"]

    BindPrompt["引导用户绑定开球网<br/>(获取更准确数据)"]

```

#### 积分同步冲突处理

| 冲突场景 | 处理策略 | 说明 |
|---------|---------|------|
| 用户手动改了积分后 API 同步了新值 | 开球网数据覆盖手动值 | 开球网为权威数据源 |
| API 返回积分与平台缓存不一致 | 更新为 API 返回值，记录变动历史 | API 是 source of truth |
| API 连续 3 次同步失败 | 降级为手动模式，7 天后重试 | 避免频繁无效请求 |
| 用户在平台比赛获得积分 | 仅平台内部记录，不同步到开球网 | 平台不反向写入开球网 |

#### API 健康检查与降级恢复

- **健康检查**：Celery Beat 每 10 分钟探测开球网 API（`GET /health`）
- **降级标记**：Redis `kqs:api_status` = `available` / `degraded` / `unavailable`
- **恢复检查**：降级状态下每 30 分钟探测一次，连续 2 次成功 → 恢复 `available`
- **缓存策略**：开球网积分缓存 Redis `kqs:rating:{user_id}` TTL 1h，降级时延长至 24h

#### 分布式追踪（OpenTelemetry + Jaeger）

Phase 1 起，所有微服务（API 网关、Celery Worker、AI Pipeline、WebSocket 网关）集成 OpenTelemetry SDK，实现请求级分布式追踪，覆盖以下场景：

| 追踪场景 | 关键 Span | 说明 |
|---------|----------|------|
| AI 分析全链路 | `api.upload_complete` → `celery.analyze_task` → `pipeline.pose_detect` → `pipeline.stroke_classify` → `pipeline.llm_analyze` → `celery.training_advice` → `celery.dashboard_bust` | 端到端耗时分解，定位 GPU/LLM 瓶颈 |
| 记分牌实时推送 | `api.score` → `redis.incr_seq` → `ws.broadcast` | 记分延迟排查 |
| 会员支付流程 | `api.create_order` → `wechat.pay_api` → `api.pay_callback` → `membership.activate` | 支付超时定位 |
| 跨模块缓存失效 | `celery.dashboard_bust` → `redis.delete_keys` | 缓存击穿排查 |

**配置要点**：

- **SDK**：Python 服务使用 `opentelemetry-distro` 自动 instrumentation，覆盖 FastAPI、Celery、Redis、SQLAlchemy、HTTPX
- **采样率**：Phase 1 设 10% 采样（`OTEL_TRACES_SAMPLER_ARG=0.1`），生产稳定后降至 5%；错误请求 100% 采样
- **Exporter**：OTLP gRPC 推送到 Jaeger Collector（`OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4317`）
- **Span 关联**：Celery 任务通过 `traceparent` header 传递上下文，保证异步任务链路连续
- **部署**：Jaeger All-in-One 单容器部署（Phase 1），Phase 2+ 拆分 Collector + Elasticsearch 存储

> **成本控制**：Jaeger All-in-One 内存模式约 512MB，10% 采样下每日 Span 量预估 < 50 万，单节点足够。采样率可通过环境变量动态调整，无需重启服务。

> - **启动失败机制**：生产环境部署时若 `JWT_SECRET_KEY` 未设置，应用应拒绝启动（`raise RuntimeError("JWT_SECRET_KEY must be set in production")`），防止使用公开已知密钥签发 JWT token。
> - **强制必填实现**：建议使用 `pydantic-settings` 的 `Field(..., env="JWT_SECRET_KEY")` 强制必填，确保未配置时在配置加载阶段即失败，而非运行时才发现：
>   ```python
>   from pydantic_settings import BaseSettings
>   from pydantic import Field
>
>   class Settings(BaseSettings):
>       jwt_secret_key: str = Field(..., env="JWT_SECRET_KEY")  # 无默认值，未设置时启动即报错
>   ```
> - **密钥要求**：生产环境密钥长度应 ≥ 32 字节，使用 `secrets.token_urlsafe(32)` 生成，禁止使用 `change-me-in-production` 等占位符。

### 14.5 密钥管理与轮换策略 (KEY-002 修复)

- **存储**: Phase 1 使用环境变量 + .env 文件（不入 Git）；Phase 2 迁移至 AWS KMS / 阿里云 KMS
- **轮换周期**:
  - JWT_SECRET_KEY: 每 90 天轮换，支持双密钥过渡期（新旧密钥同时验证 7 天）。JWT Header 携带 `kid`（key ID）字段标识签发密钥，轮换时新密钥 `kid=v2`、旧密钥 `kid=v1`，验证时按 `kid` 查找对应密钥，过渡期内两个 `kid` 均可验证
  - WECHAT_APIV3_KEY: 按微信平台要求轮换
  - OSS_ACCESS_KEY/SECRET: 每 180 天轮换
- **轮换流程**: 新密钥写入环境变量 → 旧密钥保留 7 天用于验证存量 token → 7 天后移除旧密钥
- **审计**: 每次密钥轮换记录到 audit_log

## Anti-Hallucination 约束

1. **技术版本**：必须与本设计文档第 2 节表格一致，不得编造版本号
2. **跨平台框架**：确定为 Taro 4 (React 体系)，不使用 uni-app
3. **后端语言**：确定使用 Python (FastAPI)，不使用 Node.js / Go
4. **数据库**：确定使用 PostgreSQL + PostGIS，不使用 MongoDB（理由见 2.7 节）
5. **后端架构**：统一 FastAPI 后端，不使用微信云开发双后端方案（理由见 2.7 节）
6. **AI 模型**：球体检测使用 TTNet/TrackNetV5（非通用 YOLO）；追踪使用卡尔曼滤波（非 DeepSORT）；动作识别使用 Temporal CNN
7. **3D 引擎**：确定使用 Three.js + React Three Fiber（非 Unity WebGL）
8. **3D 模型**：ReadyPlayerMe + Blender 自主制作（非真人/动捕数据）
9. **模块命名**：所有后端模块使用 snake_case，位于 `app/api/v1/` 和 `app/services/` 下；模块矩阵名称 = API 目录名称（见 4 节命名一致性约束）
10. **API 前缀**：所有业务 API 挂载在 `/api/v1` 下
11. **响应格式**：统一 `{code, message, data, timestamp}` 四字段结构
12. **模型注册**：新增 SQLAlchemy 模型必须在 `app/models/__init__.py` 中导入
13. **AI 服务独立部署**：AI 推理服务 (`ai_inference/`) 部署在 GPU 实例，不与主业务服务混部
14. **球速精度**：误差 20-30%，展示时必须使用范围值并标注"估算"
15. **积分体系**：不自建独立积分体系，延用开球网积分
16. **创作者分成**：不低于 75-80%，平台抽 20-25%
17. **视频转码**：AI 分析输入必须标准化为 1080p/30fps/H.264；多清晰度输出与 AI 分析并行
18. **AI 熔断**：连续 5 次失败触发熔断，60s 后半开探测；LLM 降级由 `LLM_ENABLED` 环境变量控制
19. **乒乓大数据**：间接胜利遍历深度限制 4 层，结果 Redis 缓存 TTL 24h
20. **数据留存**：原始视频 90 天热存储 → 1 年冷存储 → 删除；用户注销 72h 内删除个人信息
21. **搜索服务**：Phase 1-2 使用 PostgreSQL 全文搜索；Phase 3+ 评估 Meilisearch（非 Elasticsearch）
22. **内容审核**：文本 DFA 敏感词过滤；图片/视频使用阿里云内容安全 API
23. **跨端策略**：Phase 1 小程序优先（83% 功能原生），重功能通过 web-view 嵌入 H5 降级；App Phase 2+ 补充，iOS/Android 一套 RN 代码
24. **H5 降级**：H5 降级页面复用 Taro H5 编译产物，不额外开发；认证通过一次性 H5 Token 透传（5 分钟过期）
25. **小程序分包**：主包 ≤2MB（5 Tab + 认证 + 公共组件），按 Tab 拆分 4 个分包各 ≤2MB，总计 ≤8MB
26. **训练建议**：训练建议必须基于历史数据对比（进度快照 + 技术趋势），不可仅基于单次分析报告；每次分析后自动生成进度快照并更新趋势
27. **进度快照**：每次 AI 分析完成后自动生成一条 `progress_snapshot` 记录；快照永久保留作为趋势分析基础数据
28. **方案调整**：训练方案检测到停滞（连续 3 次分析无改善）时自动触发方案重新评估；调整记录版本化存储
29. **OSS 直传**：视频上传采用 STS Token 直传 OSS（不经后端中转）；对象 Key 使用 UUID 不含原始文件名；上传后必须 HEAD Object 校验确认
30. **WebSocket 重连**：客户端断连后指数退避重连（1s→2s→4s→8s→16s），最多 5 次；重连后触发全量状态同步（sync_match / sync_analysis）
31. **比赛状态机**：比赛状态为 `setup → in_progress → finished/abandoned`，记分 API 仅在 `in_progress` 状态下可用；多设备通过 Redis 原子 INCR 生成比分序号保证一致性
32. **订阅续费**：Phase 1 采用手动续费（到期前 3 天提醒），Phase 2+ 引入微信支付委托代扣自动续费；权益到期后用户数据只读降级，不删除
33. **免费额度**：Redis Key `quota:analysis:{user_id}:{date}` 原子 INCR 扣减，TTL 自然过期重置（至次日 00:00:00+1h），超限后 DECR 回退不误扣
34. **OSS 生命周期**：原始视频 90 天转 IA 冷存储、365 天删除；标准化中间产物 90 天删除；孤儿文件 1 小时清理；所有规则通过 OSS Lifecycle 配置自动执行
35. **分享机制**：分析报告分享通过独立 `/share/{token}` 路由（不暴露 API 端点），7 天有效；分享内容为摘要（不含训练建议/历史趋势等会员专属数据）
36. **创作者结算**：收益月度结算（每月 1 日），最低提现 ¥100，微信支付商户转账到零钱；退款 24h 内全额退并标记 `reversed`
37. **3D 模型版本**：模型文件以 `{model_id}_v{version}.glb` 版本化命名，新版本上线不影响已引用旧版本；训练方案引用 model_id 自动取最新 published 版本
38. **开球网降级**：API 不可用时降级为手动输入积分，Redis `kqs:api_status` 标记状态，连续 3 次同步失败进入降级模式，7 天后重试
39. **Phase 归属统一**：B 端工具（俱乐部/学员/批量分析）和球馆在线订场 SaaS 统一归入 Phase 5；需求 v0.4 已同步更新（原标 Phase 4，现已归入 Phase 5）
40. **训练负荷分析**：训练量与积分变化的 Pearson 相关系数在月度报告中计算，|r| < 0.3 视为无关联；趋势预测使用简单线性回归（非 ML 模型），R² < 0.4 时不展示预测
41. **PDF 导出**：月度报告 PDF 使用后端 WeasyPrint 渲染（HTML→PDF），图表使用 pyecharts 静态渲染嵌入；导出文件 OSS 临时存储 7 天
42. **实体奖牌**：归入 `ecommerce` 模块 `merchandise` 子分类，复用电商订单/物流/支付流程，不独立建模块
